## Пять задач Health/Recovery

`planning/health-task-cards.json` содержит SN-045–049. Для каждой заданы зависимости, requirements, AC, proposed implementation/test paths, fixture, интерфейс и измеримые assertions. `planning/health-execution-binding.json` закрепляет входные hashes, общие условия, изменение SN-042 и точные связи с текущим MCP-планом.

| Задача | Результат | Реальная проверка |
| --- | --- | --- |
| SN-045 | Health registry, poll/dispatch freshness, eligibility и noop canary | Остановить polling при живом HTTP; потерять notify; отличить ручную паузу/занятый слот от зависания |
| SN-046 | Отдельный Supervisor с собственным journal и heartbeat witness | Остановить control/основную БД; journal/уведомление продолжаются, новых claims нет; restart не обнуляет бюджет |
| SN-047 | Typed Recovery Executor и reconciliation | Lost ack, старый worker, конкурирующий deploy; нет второго эффекта, unsafe rollback, чужого target или сброса stop |
| SN-048 | Мобильные incidents и независимые alerts | Primary outbox/channel down, reconnect, role revoke; одно уведомление и честное delivery state |
| SN-049 | Git-backed Docker-поставка и сквозной recovery acceptance | Другой сервер Coolify; deploy/redeploy/restore; сохранение данных/holds и восстановление функции без SSH-kick |

Структурный JSON-check не выполняет эти сценарии. Команды mix test по test_path задаются для будущей реализации, не заявляются выполненными. Acceptance таблица AC-97–116 исходного документа нормативна целиком: unit test отдельного Elixir-модуля не заменяет контейнерный fault test, второй failure domain или реальную установку на другом сервере.

Новые карточки planned/admitted=false. Общие limits/release/evidence/handoff/non_goals берутся из исходного SN-031 pinned v0.5, не из aggregate после refinement. Конкретные proposed paths требуют проверки при реализации; файлов ещё нет. Архитектура Supervisor должна исключать обязательный запуск основной Repo/PostgreSQL в его независимом процессе. Отдельный контейнер сам по себе этого не доказывает.

## Совмещение с MCP без циклов

У действующего кандидата MCP две необходимые поправки уже заданы: SN-031 зависит от W06 как агрегат; SN-032 получает foundation от W02.02. Они сохраняются.

При принятии Health-источника применить строго проверяемые изменения:

1. Добавить SN-045–049 один раз; SN-042 дополнительно ждёт SN-049.
2. MCP SN-031.W04.03 дополнительно ждёт SN-047: инструменты recovery не принимаются раньше своего доменного исполнителя.
3. MCP SN-031.W06 дополнительно ждёт SN-049: полный plugin acceptance включает переносимость и восстановление, а не только tools/list.
4. Gate `health-recovery-domain-ready` привязать к независимым accepted evidence SN-047/SN-049. Merge документа или зелёный HTTP этот gate не удовлетворяют.
5. Все остальные зависимости, статусы и допуски сохранить. Несовпадение expected_depends_on требует нового review, не автоматического union неизвестных изменений.

Проверенная проекция: MCP без Health — 58 узлов; Health без MCP refinement — 49; совместно — 63 узла, из которых SN-031 один неисполняемый агрегат, то есть 62 потенциально исполнимых узла. Ни один не admitted этой правкой. Совместная приёмка: прежние 96 AC + 20 HEAL + 20 MCP = 136 заданных сценариев.

Восстановление старой зависимости SN-032 → полный SN-031 создаёт цикл через W06, W04.05, SN-034 и SN-033; он воспроизведён. В исправленной совместной проекции циклов нет. Граф проверен по dependency vectors точного MCP source, это не повтор полного source test suite.
