# Symphony Next / Symphony Control
## Техническое задание на отдельный проект

**Версия:** 0.5 • **Дата:** 22 сентября 2026 года • **Статус:** сводная спецификация для исполнения в отдельном проекте. Включены подтверждённые голосом решения заказчика: ChatGPT/MCP, подробное ТЗ и DAG задач, реальные тесты, автономный scoped release и диагностика с конечными повторами. Продуктовые требования не являются утверждением о готовности реализации. Конкретные IDs ресурсов и доступы фиксируются отдельным readback-манифестом.

**Назначение:** самостоятельная self-hosted платформа на основе форка OpenAI Symphony: собственный таск-трекер, единое веб-управление несколькими параллельно разрабатываемыми проектами, вход через существующий Authentik, изолированные исполнители разных агентных движков, управляемый выбор моделей и размещение на сервере заказчика под управлением существующего Coolify.

**Граница поручения:** заказчик поручил закончить пакет и установить отдельный stock Symphony для разработки нового проекта. Существующий DF Assistant не изменять. Автоматический release нового проекта разрешён по заранее ограниченному манифесту и проверкам; создание новых административных полномочий не входит в полномочия агента. Отсутствующий технический доступ обозначается BLOCKED, а не запрашивается заново как согласование уже принятой цели.

## 1. Решение заказчика и границы проекта

### 1.1. Что сохраняется без изменений

Текущая разработка DF Assistant Bot и действующий Symphony на инженерном сервере 1c-db продолжают существовать независимо. Новый проект не является миграцией, заменой или обязательной зависимостью действующего контура.

**INV-01.** Запрещены изменения работающих процессов, WORKFLOW, окружения, Git/SSH-профилей, авторизации Codex, туннелей, user units, workspace, очереди и разрешений текущего DF Assistant ради разработки Symphony Control.

**INV-02.** Новый продукт получает отдельные репозиторий разработки, локальный проект в собственном трекере, deployment-ресурсы Coolify, домен, базу/DB-роли и служебные identities. До готовности трекера начальный backlog хранится в Git по разделу 17.2; создавать обязательный Linear-проект не требуется. Каждый подключённый проект получает собственные runner identity, credentials и writable volumes. Общие writable-каталоги с действующим Symphony запрещены. Существующие Authentik и Coolify используются повторно, но не чужие client secrets или DB-роли.

**INV-03.** Приём задач из проекта DF Assistant Bot и запись в pupkinson/dfassistant из нового контура запрещены политикой по умолчанию. Их возможное подключение — будущая отдельная миграционная задача с явным переключением владельца очереди.

**INV-04.** Одновременная работа старого и нового продуктов допустима только с непересекающимися проектами, задачами, workspace и полномочиями. Два исполнителя одной задачи недопустимы. Несколько разных проектов внутри Symphony Control должны исполняться параллельно; ограничение одного владельца относится к задаче/слоту, а не ко всей платформе.

**INV-05.** Интеграция Authentik ограничивается новым application/provider и относящимися к нему mappings/bindings. Нельзя ради нового продукта обновлять, пересоздавать или менять глобальные flows, существующие providers, DNS и рабочие сессии других приложений. Нужная общая инфраструктурная доработка требует отдельного согласования.

### 1.2. Название и целевой результат

Рабочее название — **Symphony Control**. Это название документа, а не утверждение, что репозиторий или локальный проект уже созданы.

Пользователь должен через браузер создавать проекты и задачи, работать с backlog/доской/списком, назначать исполнителей, обсуждать и связывать задачи, управлять сроками и этапами, разрешать агентную обработку выбранных задач, наблюдать выполнение, отвечать агенту, принимать или отклонять допустимые запросы разрешений, отправлять результат на review и разбирать восстановление после сбоев. Для человека и агента используется одна каноническая карточка, а не два синхронизируемых backlog.

Постановка задач и управление ежедневной работой не должны требовать SSH/tmux. Аварийное обслуживание инфраструктуры остаётся задачей оператора, а не веб-терминала агента.

### 1.3. Принятое размещение и идентификация

**DEC-01 — решение заказчика:** используем существующий Coolify. Новый Google Cloud-проект, Google VM или вторую установку Coolify не создаём. Точный подключённый сервер/destination и доступная ёмкость устанавливаются перед provisioning; слово Coolify не означает автоматически тот же физический хост, где работает его управляющий сервис.

**DEC-02 — решение заказчика:** вход через уже развёрнутый Authentik. Для нового веб-продукта заводится собственный confidential OIDC client/application в существующем IdP. Пользователи и их SSO остаются в существующем каталоге. Отдельная password database или Basic Auth как штатная замена SSO не допускаются. [S7]

**DEC-03 — решение заказчика:** параллельная разработка двух и более проектов входит в первую принимаемую версию, а не откладывается на следующий релиз. У каждого проекта свои workflow, локальная очередь, репозитории, агенты и область доступа.

**DEC-04 — решение заказчика:** собственный таск-трекер вместо Linear входит в MVP. Control, tracker, API, поиск, persistent state, in-app inbox и хранилище вложений размещаются на сервере заказчика через Coolify; вход обслуживает уже существующий Authentik. Требование не подменяется установкой другого стороннего трекера либо UI-оболочкой над Linear.

**DEC-05 — граница автономности:** в production-профиле нового продукта нет обязательных аккаунта, токена, webhook, SDK-вызова, платной лицензии или доступности Linear. Нельзя скрыто возвращаться к нему при ошибке локального трекера. Обязательный облачный сервис для поиска, хранения задач, frontend assets или аналитики также не вводится. Код/модели, package registries, DNS/сертификаты и согласованные уведомления учитываются как отдельные внешние зависимости, а не называются локальными.

**DEC-06 — решение заказчика:** платформа не привязана к Codex. Оператор может выбрать разрешённые движок/модель; оркестратор может предложить или выбрать их в пределах versioned policy, учитывая сложность, риск и затраты. «Самый дорогой» и «самый дешёвый» не считаются доказательством оптимальности.

**DEC-07 — решение заказчика:** повседневное управление доступно с телефона: задача, обсуждение, запуск, контроль, ответы, разрешения, бюджет, review и остановка. Предложение реализации — PWA; отдельные native Android/iOS applications не входят в первую поставку.

Развёртывание нового продукта: Git-backed Coolify Application для control core и отдельные Git-backed runner-ресурсы для проектов. Compose-манифесты хранятся в Git; выпуск следует согласованному PR/CI/webhook path. Не использовать pasted Compose Service как скрытую замену репозиторному release flow. Coolify различает эти типы ресурсов. [S5]

Разрешение на отдельный bootstrap дано заказчиком. Provider, repo, домен и Coolify resources создаются только в выделенной области по typed provisioning manifest; наличие делегации не доказывает наличие прав у текущего инструмента.

### 1.4. Что означает «полностью на нашем сервере»

| Контур | Требование v0.4 |
| --- | --- |
| Задачи и управление | Собственные UI/API, tracker, scheduler, БД, локальный поиск, история, вложения и inbox; у заказчика под Coolify |
| Вход | Уже существующий self-hosted Authentik; новые пользователи не обязаны иметь Linear или GitHub account для работы с задачами |
| Исполнение | Runner и выбранный агентный процесс на сервере заказчика; по умолчанию модели остаются внешним сервисом по выбранному model profile |
| Код и проверки | GitHub/разрешённый CI сохраняются как отдельные интеграции; отказ Git не блокирует ручное ведение задач, но блокирует действия, которым нужен этот Git |
| Эксплуатация | Backup на отдельной контролируемой площадке/failure domain; отсутствие внешнего SaaS-трекера не означает отказ от резервной копии вне основного сервера |

Автономное локальное вычисление моделей, перенос GitHub в локальную forge и air-gapped эксплуатация не включены автоматически. Для профиля с внешней моделью без доступа к её провайдеру агент не выполняет новый model turn, но доступные UI/БД/Authentik позволяют продолжать ручное планирование. Код и часть контекста задач могут передаваться модели и Git-провайдеру; это явно отражается в реестре данных и согласованных egress-разрешениях. [S4]

## 3. Объём продукта и исключения

### 3.1. Первая принимаемая версия — MVP

Один внутренний tenant и N независимых подключённых проектов. Приёмка требует минимум два проекта с одновременно активными model turns в отдельных runner-контейнерах. По умолчанию один concurrent slot на проект и global_limit = 2 для первого пилота; расширение до N выполняется конфигурацией и provisioning, без изменения исходного кода. Многопроектность не означает публичный SaaS или доказанную изоляцию взаимно недоверенных организаций.

Первая принимаемая версия включает два протестированных agent adapters, registry разрешённых моделей, ручной/рекомендательный/автоматический выбор, бюджетный контроль, безопасный handoff, mobile PWA и требования разделов 18–21 с отметкой «первая версия». Она также включает собственный многопроектный таск-трекер с возможностями раздела 5; защищённый dashboard; подключение runner; карточки задач и выполнения; Authentik и project roles; pause/resume intake, interrupt/stop; ответы на вопросы и scoped approvals; retry/recovery; versioned workflow; native tracker adapter и GitHub-интеграцию; локальные уведомления; persistent state/audit; backup/restore и release/rollback. Для задач, не требующих агента, полноценное ручное ведение доступно без model credentials и provisioning runner.

Результат инженерной задачи зависит от контракта: код → PR/checks/review; поставляемый этап → разрешённый auto-merge, webhook-deploy и runtime acceptance. Без дополнительного человеческого подтверждения каждого обычного деплоя внутри заранее согласованной области. In Review не является искусственной остановкой всего проекта: отдельная review/release-стадия проверяет exact artifact и продолжает выполнение при выполненных gates. Собственный tracker — существенный самостоятельный модуль, а не дополнительная форма dashboard; план/оценка реализации v0.3 не переносятся на v0.4 без пересмотра объёма. Здесь «MVP» означает первую принимаемую версию большого продукта, не обещание короткой разработки.

### 3.2. Следующие версии

После acceptance MVP: несколько одновременно работающих агентов внутри одного проекта; динамическое autoscaling уже provisioned runner сверх первой фиксированной топологии; дополнительные adapters сверх первых двух, локальные model profiles и дополнительные Git profiles; расширенные canary/traffic-splitting стратегии сверх базового scoped webhook release; сложные portfolio-roadmap/ресурсное планирование, произвольные custom fields, advanced analytics и необязательный импорт из сторонних трекеров. Базовые циклы/этапы, сохранённые представления и зависимости уже входят в MVP.

### 3.3. Не входит

Новый оркестратор с нуля вместо форка; замена Elixir/Phoenix без ADR; обязательные Kubernetes/Kafka/Redis/внешний search engine/SPA без доказанной необходимости; произвольный SSH/web-terminal; root/Docker-доступ агента; самостоятельная модификация policy; обновление исполняющего себя runtime без внешнего release-контроля; миграция действующего DF Assistant; безусловный auto-approve; публичная регистрация; биллинг SaaS; сбор истории браузера. Не обещается буквальное копирование всех функций/дизайна/API Linear, мобильные native clients, online-совместное редактирование через CRDT или обязательная двусторонняя синхронизация с внешним трекером.

## 4. Архитектура и обоснование

### 4.1. Выбранный подход

**Форк штатного Elixir/OTP Symphony с развитием Phoenix/LiveView и встроенным собственным tracker.** Начальная архитектура — модульный монолит управляющего сервиса: Tracker, Execution, Agent Registry/Routing/Budget, Identity/Policy, Integrations и Audit/Notifications имеют отдельные доменные контракты, но не требуют отдельных сетевых микросервисов. Общая БД продукта позволяет транзакционно связать разрешённое изменение задачи, admission intent и outbox. Runner остаются отдельными контейнерами.

Не выбраны: внешний UI над неизменённым Symphony/Linear, потому что он не выполняет требование собственного backlog и durable управления; отдельный сторонний self-hosted tracker, потому что заказчик запросил свой; полное переписывание scheduler, потому что оно добавляет повторную реализацию. Отдельный микросервис собственного tracker возможен позже по измеренной необходимости, но в MVP добавляет распределённые транзакции без обязательной пользы.

Разделение ниже — границы ответственности, не поручение создать набор независимых планировщиков.

### 4.2. Состав и независимость deployment

| Компонент | Ответственность | Граница доступа |
| --- | --- | --- |
| Control core + native tracker | Единый Phoenix UI/API, карточки/доски, Authentik OIDC, RBAC, scheduler, команды, workflow, audit/outbox | Без Docker socket, произвольного shell, широкого Coolify API и доступа к production |
| Runner проекта A | Один слот, supervisor и выбранный adapter/agent engine, workspace и toolchain только A | Project-bound identity; нет DB/admin/deploy credentials |
| Runner проекта B … N | Аналогичные независимые слоты других проектов | Не читает данные A, не исполняет его команды |
| PostgreSQL продукта | Проекты/задачи/комментарии/история/поиск; отдельно execution state, leases, approvals, outbox/audit | Отдельная от DF Assistant/Authentik база; доступ только control и миграциям |
| Хранилища | Раздельные workspace и engine-specific HOME/session state; защищённые вложения tracker, документы и run artifacts | Без общих writable mounts и cross-project cache |
| Существующие edge и Authentik | HTTPS-вход и единый каталог пользователей/SSO | Не дублируются; новая интеграция не меняет чужие приложения |

**Один UI, один канонический tracker и один логический scheduler, но отдельные исполнители.** Два проекта требуют минимум двух runner-контейнеров сверх control и DB. Для tracker не нужен отдельный контейнер только ради формального разделения. Runner получает назначенную attempt от control; самостоятельно не выбирает задачи ни из локальной БД, ни из внешнего backlog.

**ARCH-01.** Core и проектные runner — отдельные Coolify Application/Compose-ресурсы с независимыми release manifests. Обновление runner A не должно пересоздавать runner B. Один общий стек со всеми проектами не выбирается как production default: stack-level lifecycle связывает их обновления. [S5, S14]

**ARCH-02.** В MVP runner заранее разворачивает оператор штатным repository/PR/CI/webhook path. UI регистрирует проект и показывает потребность в provisioning, но не создаёт Docker-контейнеры широким API-ключом. Добавление очередного проекта требует новых конфигурации/ресурса/identity, а не нового кода или второго scheduler.

**ARCH-03.** Control → runner: частный аутентифицированный transport с project/slot identity, attempt и fencing epoch; сертификат/credential A не подходит для B. У агента нет прямого доступа к transport credential управляющего процесса. Native agent servers, включая Codex App Server, наружу не публикуются.

**ARCH-04.** Агент исполняет недоверенный код. UID, mounts, секреты и процессы отделены от supervisor. Нет privileged, host PID/network или Docker socket. Совместимость sandbox и контейнерного hardening подтверждается exact-version тестами, не обходится незаметным ослаблением защиты. [S11]

**ARCH-05.** Один runner slot закреплён за одним project_id и не переиспользуется между проектами. Раздельны workspace, HOME/engine-state (включая CODEX_HOME), временные файлы, Git config/keys, model-session state, tool/MCP bindings и журналы. Общим может быть immutable базовый image; mutable dependency caches по умолчанию раздельны.

**ARCH-06.** Проекты имеют отдельные private networks; разрешён только нужный transport к control и согласованный egress. Runner не подключается к общей сети всех production-сервисов ради удобства. Конкретный маршрут между ресурсами фиксируется до deploy и проверяется отрицательными сетевыми тестами: отдельное Compose-имя само по себе не является полным security boundary. [S12]

**ARCH-07.** Control и его DB остаются общими зависимостями нового продукта: их сбой может затронуть все проекты. Разделение runner не обещает HA или защиту от компрометации общего ядра хоста. Для взаимно недоверенных организаций/особо опасных workloads нужен отдельный host/VM либо усиленный runtime по отдельному ADR; выбирать его автоматически не требуется. [S11]

### 4.3. Контракт подключённого проекта

**PRJ-01.** Project descriptor содержит immutable project_id, уникальный ключ проекта, имя, владельца, memberships/роли, внутренний tracker namespace, repo bindings, issue-status scheme, workflow/policy versions, allowed engine/model profiles, selection mode, routing policy, data classification, runner resource/slot, credential references, allowed tools/egress, квоты, notifications и retention. Все bindings разрешаются сервером, а не доверяются браузеру/агенту. Проект допускает режим tracker-only без подключения исполнителя.

**PRJ-02.** У A и B независимые WORKFLOW: инструкции, статусы/метки, модели в разрешённом профиле, hooks, timeout/retry rules и политика согласования. Общий шаблон допустим как versioned read-only основа; изменение шаблона не обновляет все проекты молча.

**PRJ-03.** Подключение исполнения: draft → validated → provisioning_required → ready → enabled. Локальный tracker проекта доступен после создания проекта и проверки ролей; он не ждёт runner. Admin отдельно задаёт репозиторий, admission policy и agent workflow; оператор разворачивает scoped runner; readback проверяет image/identity/network/storage/provider access/capability matrix. Только затем агентное исполнение enabled. Нет своего runner — automation blocked, а не запуск в чужом контейнере.

**PRJ-04.** Deactivate закрывает admission только проекта; archive допускается после drain и readback. Удаление project record не означает удаление volumes/секретов/артефактов. Destructive cleanup — отдельная подтверждаемая операция.

**PRJ-05.** Каждая native issue принадлежит ровно одному project_id. Repo bindings исполняемых проектов в MVP непересекающиеся; совместный repo требует будущего явного режима координации. Cross-project ссылки на задачи не дают доступа к чужой карточке или полномочий на её исполнение. DF Assistant исключён независимо от числа новых проектов.

## 5. Собственный таск-трекер и модель данных

### 5.1. Проверяемая функциональная граница


Сходство с Linear означает функциональные возможности для нашего инженерного процесса, а не обещание полного клона. В ориентире есть проекты, зависимости, доски и сохранённые представления; ниже перечислено, что именно реализуется у нас. Чужой SaaS, визуальные assets и API не становятся частью runtime. [S16–S18]

| Область MVP | Обязательные возможности |
| --- | --- |
| Проекты и участники | Каталог, ключ/описание, владелец, memberships, архив; свои статусы, agent workflow, repo/runner/лимиты; tracker-only режим |
| Карточки | Стабильный ID, заголовок, Markdown-описание, критерии приёмки, тип, приоритет, статус, ответственный, автор, метки, срок, оценка и timestamps |
| Рабочие представления | Backlog/triage, канбан с drag-and-drop и доступным альтернативным действием, список, группировка/сортировка, сохранённые фильтры, «Мои задачи» |
| Декомпозиция и связи | Parent/sub-issues, checklists, blocks/blocked-by, related, duplicate-of; граф без циклов для blocking и родительских связей |
| Планирование | Этапы/milestones, необязательные циклы со start/end, назначение задач в этап/цикл, просрочки и базовый отчёт прогресса |
| Совместная работа | Комментарии, упоминания, подписки, единый agent workpad, вложения, версии Markdown-документов/ТЗ проекта, история изменений |
| Поиск и операции | Локальный поиск по ID/тексту, составные фильтры, ограниченные bulk edits с preview, шаблоны задач, экспорт/импорт собственного формата |
| Связь с исполнением | Явный admission, task↔runs↔attempts, вопросы/approvals, тесты, commit/PR и review в карточке; задача доступна и без агента |
| Управление и отчёт | Project roles, аудит, in-app inbox, counts/age/lead/cycle-time и источники метрик; архив вместо автоматического удаления |

**TSK-01. Идентичность.** Каноническая issue имеет UUID и монотонный номер в проекте; читаемый ключ вида SC-123 — ссылка, не полномочие. Номер не переиспользуется после удаления/архива. Первоначальный project key в MVP immutable; внешние IDs при импорте остаются отдельными references и не определяют внутреннюю identity.

**TSK-02. Карточка.** Обязательны project_id/title/type/status/creator; description и acceptance criteria редактируются безопасным Markdown. Типы по умолчанию task/bug/feature/research; priority — none/low/medium/high/urgent. Срок и необязательная оценка не являются обещанием времени работы модели. Хранятся UTC timestamps, в UI — явно выбранная timezone пользователя.

**TSK-03. Ответственность.** Responsible assignee — участник проекта либо не назначен; текущий исполняющий агент/attempt — отдельное поле. Назначение человека не передаёт его OIDC session агенту. Автор-человек, сервисная identity, бот и imported legacy author различаются; нельзя приписать агентное изменение человеку.

**TSK-04. Список и доска.** Оба представления читают одни и те же записи и фильтры. Drag-and-drop меняет статус/порядок только через серверную команду с expected_version; запрещённый переход возвращает карточку с причиной. Ручной rank стабилен; фильтры и сортировка не меняют scheduler priority скрыто. «В очереди агента» — отдельный вид, а не весь Todo.

**TSK-05. Статусы проекта.** Свои имена и порядок статусов с устойчивыми ID/категориями triage/backlog/unstarted/started/review/completed/canceled. Начальный шаблон: Triage, Backlog, Todo, In Progress, In Review, Done, Canceled. Issue-status scheme и исполняемый WORKFLOW — разные versioned объекты. Переименование столбца не меняет его категорию и admission semantics; удаление используемого статуса требует preview/mapping и блокируется при незавершённом конфликте.

**TSK-06. Связи и зависимости.** Parent/sub-issues, blocking и duplicates не допускают self-link и циклы; связанные IDs валидируются в одной транзакции. По умолчанию only completed удовлетворяет blocker; Canceled/Duplicate не означают выполненную зависимость. Duplicate разрешается через проверенный canonical target. Reopen blocker переоценивает ещё не стартовавших dependents; уже работающим ставится hold/операторское решение, а не невидимый rollback.

**TSK-07. Межпроектные связи.** По умолчанию отношения локальны проекту. Межпроектная ссылка разрешается только пользователю с доступом к обеим сторонам и соответствующими правами. В MVP она информационная: не запускает и не изменяет чужой проект. Агенту не раскрываются закрытые названия/описания/счётчики. Cross-project blocking, автоматическое разблокирование другого проекта и общий workspace не вводятся без отдельного режима координации.

**TSK-08. Комментарии и документы.** Комментарии, упоминания, версии description/acceptance criteria и проектных Markdown-документов сохраняют автора/время/версию. Удаление или редактирование отображается в истории; audit нельзя переписать. Один mutable agent workpad на issue + append-only evidence refs; upsert не создаёт новый комментарий при каждом retry. Комментарий не трактуется как команда агенту: для ответа/steer нужна явная операция UI.

**TSK-09. Локальный поиск.** По ID/title/description, меткам и доступным комментариям; фильтры по проекту, статусу, assignee, автору, типу, priority, сроку, этапу/циклу и наличию блокировки. В MVP — PostgreSQL full-text + exact ID search, без обязательного внешнего search SaaS/embedding API. ACL применяется до выдачи snippets/counts и в live updates; индекс восстанавливаем из БД. [S19]

**TSK-10. Представления и bulk actions.** Личные/проектные saved views, подписки, «созданные мной/назначенные мне/требуют внимания», копируемые внутренние ссылки. Ссылка не выдаёт права. Bulk edits ограничены 100 карточками за операцию по умолчанию, имеют preview версий и affected count. Транзакционный all-or-nothing для разрешённого набора; конфликт не скрывается частичным success. Bulk approve, force-stop и массовый agent enqueue без отдельного preview запрещены.

**TSK-11. Milestones и циклы.** Этапы задают именованные deliverables/целевые даты; циклы — необязательные интервалы планирования проекта. Задача может принадлежать одному активному циклу и одному milestone. Автоперенос незавершённого остатка не выполняется молча: preview и явное решение. Прогресс считается по явно выбранной формуле count/estimate; Done, awaiting_review и canceled показываются раздельно.

**TSK-12. Уведомления.** Inbox — локальные durable записи: mention/assignment/status/blocker, вопрос/approval, failed/recovery/review. Только подписчики с актуальными правами. Notification delivery и пользовательское read/ack различаются; события дедуплицируются. Внешний SaaS/Telegram не обязателен; email через согласованный SMTP или другой канал подключаются независимо, без утечек закрытого контента.

**TSK-13. Вложения.** Байты лежат в project-scoped storage на сервере заказчика, metadata/hash/size/type/owner — в БД. По умолчанию не более 25 MiB на файл и отдельная project quota; значения настраиваются. Upload не создаёт публичный URL. Проверяются extension/media mismatch, опасный HTML/SVG, zip/traversal, XSS и secrets; подозрительный файл quarantine. Агент получает только явно разрешённый snapshot, а не весь каталог файлов проекта.

**TSK-14. Экспорт/импорт.** Версионированный native JSON/Markdown export + manifest/checksums вложений. Включает структуру, ID, статусы, связи, документы, комментарии и происхождение; исключает secrets/sessions/live leases и исполняемые полномочия. Изолированный restore сохраняет внутренние ID; импорт в существующую среду создаёт проверяемую source→target ID mapping и не переписывает чужие записи. Сначала preview/validation/duplicate search, затем bounded write и count/hash readback; повтор import_batch/source ID не дублирует данные. Импортированные задачи имеют automation disabled независимо от исходного статуса.

**TSK-15. Архив и перемещение.** Archive обратим и не удаляет evidence; hard purge — отдельная retention операция с правом/preview/hold checks. Активную issue нельзя переносить между проектами. В MVP перенос после drain выполняется как явное создание новой issue с provenance link и архивирование прежней, без копирования секретов, разрешений, live attempts и недоступных получателям материалов.

**TSK-16. Ручная работа и шаблоны.** Contributor может создавать/обсуждать/вести разрешённые карточки без права запускать или одобрять команды. Шаблон bug включает Problem/Evidence/Root cause или UNKNOWN/Impact/Expected/Regression/Minimal fix/Acceptance/Dependencies. Шаблон задачи содержит цель, scope, ограничения и acceptance. Заполнение шаблона агентом не подтверждает эти поля как проверенные факты.

**TSK-17. Отчёты.** Сводки только разрешённых проектов: backlog/overdue, waiting attention, blockers, throughput, время до начала/до завершения/review. Формулы и временное окно показаны; человеческие статусы, runtime timestamps и measured token usage не смешиваются. Неполная история обозначается UNKNOWN/partial, а не нулём. Автоматическое ранжирование сотрудников по «эффективности ИИ» не требуется.

**TSK-18. Права и автоматизация.** Сервисные tools читают task context, upsert workpad, добавляют evidence, создают draft bug/subtask и запрашивают In Review только в scope текущего назначения. Создание новых задач агентом имеет лимит/дедупликацию; они поступают в Triage без права самозапуска. Агент не изменяет roles, workflow/policy, admission, blocker completion, архив/Done чужой задачи и не выдаёт себе новый проект. На все пути распространяются SEC/CMD и audit.

### 5.2. Источники истины и долговечные сущности

**DATA-01.** PostgreSQL собственного продукта — authoritative source задач, бизнес-статусов, комментариев/workpad, документов и отдельного состояния исполнения. Tracker и Execution — разные домены одной БД, не зеркала Linear. GitHub — источник commits/PR/checks; runner — источник наблюдений о процессе. UI cache/search index/outbox не являются альтернативным backlog.

**DATA-02.** Минимальные сущности: projects/memberships; issue_status_schemes/statuses, issues/revisions, labels/issue_labels, issue_relations, comments/workpads, documents/document_versions, attachments, cycles/milestones, saved_views/subscriptions, issue_activity/import_batches; repository_bindings, workflow_versions/policy_versions; runs/attempts, runner_slots/bindings, project_limits/provider_quota_pools, leases, commands, approval_requests/user_inputs, run_events/artifacts, provider_operations, engine_profiles/model_catalog_snapshots/routing_decisions, task_stage_runs/handoff_manifests, budget_reservations/usage_events/cost_reconciliations, evaluation_sets/evaluation_runs, device_push_subscriptions, outbox_messages/notification_deliveries/audit_events. Это логическая схема для проектирования migrations, не существующие production tables.

**DATA-03.** Issue — задание; run — его логическое выполнение; attempt — конкретный запуск. Retry создаёт новую attempt, не стирая старую. Каждый run ссылается на native issue_id/project_id и immutable execution snapshot описания, критериев, разрешённых комментариев/вложений. Внутреннее представление work item у adapter не создаёт вторую каноническую карточку.

**DATA-04.** Для attempt сохраняются upstream/fork/agent/adapter versions, requested/resolved/observed model identity, catalog/routing versions, stage/role, image digest, workflow/policy hashes, repo URL, base/head/tree SHA, branch/PR, workspace identity, runner generation, timestamps и результат проверок. Недоступные поля явно UNKNOWN, не вычисляются по имени ветки.

**DATA-05.** Разрешённое изменение issue, revision/activity и соответствующее outbox/admission intent сохраняются в одной DB transaction. Claim повторно проверяет issue_version, admission, зависимости, membership/policy и свободный slot атомарно. События имеют ID и монотонную последовательность в пределах issue/run; доставка at-least-once, consumers дедуплицируют. Потеря wakeup не теряет задачу: есть периодическая сверка долговечного состояния.

**DATA-06.** Роли приложения не могут произвольно исправлять audit history. Содержимое артефактов хранится отдельно от метаданных; применяются hash, size, media type, project scope и срок хранения.

**DATA-07.** Бизнес-статус issue, admission и runtime state раздельны даже в одной БД. Агент закончил turn, PR создан, tests passed, review accepted, issue Done, merged и deployed — разные факты. Источник и timestamp каждого факта доступны в карточке.

**DATA-08.** Все проектные данные, команды, артефакты, event subscriptions и cache keys имеют обязательный project_id. Foreign keys/constraints исключают связь attempt A с request или runner B. Доступ проверяется и для direct ID, поиска, экспорта и live-stream. Общая DB не является разрешением читать все строки.

**DATA-09.** Не более одного active claim по native issue_id и slot; composite FK/constraints связывают project_id всех отношений. Зеркала импорта не могут создать второй активный владелец той же исходной задачи. Сводки/экспорты агрегируют только доступные actor проекты; служебный DB owner не выдаётся приложению/агенту как пользовательский инструмент.


### 5.3. Жизненный цикл карточки и разрешение на запуск

**ADM-01.** Создание issue, изменение Todo, назначение assignee или перенос в цикл не являются разрешением выполнять код. По умолчанию execution_mode = manual, automation admission закрыт. Для agent mode оператор явно задаёт разрешённый scope, repo, workflow/policy, критерии и execution snapshot; автоматический допуск по проектным правилам возможен только по отдельно включённой versioned policy.

**ADM-02.** «Передать агенту» выполняет fresh precheck и фиксирует allowed_for_execution отдельно от статуса. Eligibility требует native issue active, разрешённый mode/policy, удовлетворённые dependencies, собственный ready runner, лимиты и отсутствие активной attempt. Автор draft-задачи не получает Operator автоматически. В UI причина недопуска машиночитаема и понятна человеку.

**ADM-03.** Изменение acceptance criteria/scope/repo/dependencies после enqueue инвалидирует старый допуск. До запуска требуется новая проверка версии. При уже активной attempt сохраняются исходный snapshot и diff; safety-sensitive изменение закрывает последующий допуск и ставит execution hold с контролируемым interrupt/решением. Новая инструкция не впрыскивается в активный turn через обычный комментарий.

**ADM-04.** Переход в In Review фиксирует результат/evidence и закрывает дальнейший dispatch этой issue. Done требует явных критериев приёмки и полномочия на закрытие; наличие PR не достаточно. Canceled/архив отзывает допуск и инициирует bounded stop, но карточка отдельно показывает runtime stopping/unknown до readback. Reopen не восстанавливает старые approvals и не запускает агент автоматически.

**ADM-05.** В модели данных отдельно сохраняются intended issue transition и observed runtime outcome. UI не выставляет running только из-за ручного In Progress. Выдача claim и конкурентное снятие разрешения сериализуются; повторное событие/worker restart не создаёт новую попытку без актуального admission. Это проверяется race/fault tests, не эвристикой по last_updated.

## 6. Состояния, очередь и единственный владелец

### 6.1. Состояния attempt

| Состояние | Значение |
| --- | --- |
| queued | Допущена политикой, ожидает слот; исполнитель ещё не запущен |
| starting | Слот и ownership получены; идёт подготовка; model turn не доказан |
| running | Есть подтверждённый активный turn |
| waiting_input | Получен живой запрос данных от агента |
| waiting_approval | Получен поддерживаемый запрос разрешения |
| pausing / paused | Запрошена мягкая остановка / подтверждена остановка на поддерживаемой границе |
| stopping / cancelled | Остановка запрошена / прекращение зарегистрированного выполнения подтверждено |
| awaiting_review | Инженерный результат передан на review, рабочий каталог сохранён |
| failed / succeeded | Итог по явно заданным критериям задачи; succeeded не означает production deploy |
| recovering / recovery_required | Идёт сверка после потери связи / требуется решение человека |

Организационная блокировка задачи — отдельный admission hold с причиной; она не маскируется под ожидающий RPC approval. Все переходы описываются таблицей допустимых переходов и тестируются.

**STATE-01.** Project admission имеет отдельные значения enabled, paused и emergency_stopped. Pause intake не меняет состояние текущих attempts и не означает заморозку процессов.

**STATE-02.** После cold start/restart control глобальный admission закрыт до сверки DB/ownership. Затем каждый проект открывается отдельно только после своего reconciliation; unknown в A удерживает A и не блокирует исправный B при исправных общих зависимостях. Сохраняются глобальный и проектные pause/emergency намерения. При глобальном incident они имеют приоритет над project enable.

**STATE-03.** В MVP по умолчанию project_limit = 1, global_limit = 2; разные стадии/движки проекта используют этот слот последовательно, минимум два разрешённых проекта исполняются одновременно. Уникальность active claim и slot ownership обеспечивается DB constraints/transactions. Лимит в памяти и имя контейнера не являются защитой от дублей. N проектов поддерживаются конфигурацией; фактическая concurrency ограничена provisioned slots, host capacity и provider quota.

**STATE-04.** Ownership включает owner generation / fencing epoch. Просроченный владелец не может выдавать новые команды и публиковать изменения через интеграционный шлюз.

**STATE-05.** Истечение lease не доказывает остановку старого процесса. Новый attempt запрещён до подтверждённого прекращения прежнего либо доказанной изоляции/quarantine, исключающей его дальнейшие побочные эффекты.

**STATE-06.** Два экземпляра control с одной базой не могут одновременно владеть одним runner slot. Это safety requirement для accidental double start, а не обещание HA в первом релизе.

**STATE-07.** Перевод native issue в terminal status останавливает допуск и инициирует согласованную остановку. Неотправленные изменения, evidence и workspace не удаляются автоматически только из-за такого статуса.

### 6.2. Многопроектное планирование и лимиты

**SCH-01.** Новая attempt допускается только при свободном слоте её проекта, project admission enabled, отсутствии global stop и наличии global/provider permit. Атомарное резервирование не допускает превышение лимитов при конкурентных запросах.

**SCH-02.** Раздельно учитываются occupied runner slots и активные model turns. Waiting input/approval занимает свой slot, пока сохраняется сессия; ожидание A не блокирует B. Слот нельзя выдать второму агенту, лишь потому что первый не потребляет токены.

**SCH-03.** При конкуренции за общий provider/global permit используется детерминированная справедливая очередь между eligible проектами; priority действует внутри проекта. Постоянный поток A не должен бессрочно вытеснять B. Порядок и причина ожидания видны; fairness тестируется на управляемых fixtures.

**SCH-04.** Лимиты проекта: CPU/RAM/PIDs, workspace/storage high-watermark, время/turns/tokens и разрешённые model profiles. Глобально учитываются резерв хоста, лимиты control/DB и общие квоты провайдеров. Превышение лимита A закрывает его admission; общий критический resource pressure может закрыть все проекты и обозначается отдельно. [S13]

**SCH-05.** Разные контейнеры не считаются отдельными квотами модели. Для проектов, использующих один billing/account quota pool, учитывается общая квота. Отдельные model identities предпочтительны, но ни создание аккаунтов, ни копирование существующего Codex login не выполняются автоматически. UNKNOWN quota/cost показывается явно; денежный hard cap не обещается без достоверного accounting.

## 7. Веб-интерфейс и команды оператора

### 7.1. Основные экраны

**UI-01. Overview.** Переключатель проектов и сводка только разрешённых проектов: active slots/turns, admission mode, очередь, waiting input/approval, retries, freshness, квоты и недоступные зависимости. Глобальное состояние отличается от проектного. Пустая очередь и ошибка её чтения отображаются по-разному.

**UI-02. Tracker и очередь.** Встроенные backlog/доска/список, создание и редактирование issue, связи, комментарии, этапы/циклы, search/saved views. Отдельное представление agent queue показывает eligibility/hold/slot и позволяет явный enqueue. Переход в сторонний трекер не требуется; UI читает собственный Tracker domain.

**UI-03. Run detail.** Timeline, публичные сообщения агента, tool outcomes, диффы, tests/PR/checks, tokens, elapsed time, base/head SHA и workspace state. Данные недоверенного репозитория выводятся как безопасный текст/санитизированный Markdown, без исполняемого HTML. Скрытые рассуждения модели не запрашиваются и не объявляются доступными.

**UI-04. Inbox внимания.** Pending questions, approvals, recovery-required и failed notifications. Для каждого события — владелец, время, expiry, scope и допустимые действия.

**UI-05. Настройки проекта.** Собственные repo/native project bindings и issue-status schemes, workflow drafts/versions, runner readiness, limits, роли, notifications и состояние credentials без их значений. Есть create/validate/enable/pause/drain/archive с явным provisioning status. Изменения policy отделены от инструкций агенту; копирование проекта не копирует secrets, memberships или active runs.

**UI-06. Аудит и состояние платформы.** Кто, что, в каком scope запросил; accepted/applied/failed/unknown; ссылки на безопасное evidence; build/revision и backup status.

Интерфейс проектируется mobile-first для телефона и desktop, основной язык — русский. Обязателен PWA-профиль раздела 20; agent/model, причина маршрута, бюджет и freshness видны без открытия полного лога. Технические ID копируются отдельно; статус не передаётся только цветом. Потеря live-соединения обозначается явно, управляющие действия требуют свежей серверной проверки.

### 7.2. Контракт команд

| Команда | Требуемое поведение | Ограничение |
| --- | --- | --- |
| Поставить задачу в очередь | Fresh read задачи, project/repo/policy validation, idempotent claim request | Не допускает DF Assistant и чужой проект |
| Приостановить приём | Закрыть admission выбранного проекта; глобальная команда имеет отдельное право | Текущие задачи продолжаются; соседние проекты не затронуты |
| Возобновить приём | Выполнить precheck и снять admission pause | Не одобряет approvals и не снимает emergency stop |
| Приостановить задачу | Запросить остановку на поддерживаемой границе/interrupt; сохранить контекст | Не обещает SIGSTOP или checkpoint каждого внешнего процесса |
| Продолжить задачу | Проверить context, ownership, workflow/policy и отсутствие старого worker | Не считать replay старого RPC продолжением |
| Остановить задачу | Сначала interrupt; затем ограниченный stop после timeout | Завершённые побочные эффекты не откатываются |
| Принудительно завершить | Завершить только зарегистрированную группу процессов текущей attempt | Отдельное право и подтверждение; никаких PID из браузера |
| Ответить агенту | Ответить живому request или отправить отдельную инструкцию по разрешённому protocol path | Ответ не является выдачей полномочий |
| Разрешить / отклонить | Exact scoped decision для текущего запроса; проверить policy и срок | Нет кнопки безусловного approve-all |
| Повторить | Новая attempt после сверки предыдущей, workspace и внешних операций | Не слепой повтор неясного write |
| Выбрать движок/модель | Pin разрешённого профиля или режим Recommend/Auto; preview риска/бюджета | Operator не обходит platform deny; активная attempt не меняется молча |
| Передать другому агенту | Drain, readback, checkpoint/handoff manifest, новая stage attempt | Старые разрешения и mutable session state не переносятся |
| Изменить лимит расходов | Expected version, сумма/период/причина; согласование при расширении | Не меняет цену провайдера и не отменяет уже понесённые затраты |
| Передать на review | Сохранить evidence и выполнить разрешённый переход native issue | Не означает merge/deploy или Done |
| Аварийный стоп | Явный scope: текущий проект или вся платформа; закрыть admission и выполнить bounded stop | Глобальный stop требует отдельного права; внешние эффекты не отменяются мгновенно |

**CMD-01.** Любая изменяющая команда выполняется сервером с actor identity, project scope, idempotency key, expected resource version и при необходимости reason. UI не является местом enforcement.

**CMD-02.** Ответ «accepted» означает долговечную регистрацию намерения. «applied» выставляется только по фактическому подтверждению целевой операции. Неопределённый outcome отображается как unknown/recovery_required.

**CMD-03.** Состояние перед исполнением перепроверяется. Два оператора не могут дать разные решения одному request; проигравший получает conflict, а не тихий успех.

## 8. Общий агентный протокол: сообщения, approvals и recovery

**PROTO-01.** Никакого tmux send-keys, парсинга цветного terminal output или текста «одобрено» вместо протокольного ответа. Каждый adapter использует документированный структурированный API/SDK точной версии движка. Для Codex это App Server; для других движков конкретный transport определяется engine profile. [S4, S20–S24]

**PROTO-02.** Матрица поддерживаемых операций фиксируется по engine/adapter version, schema hash и тестам: start, events, input, interrupt, approval, resume, usage, model discovery/selection. Современный README не доказывает поддержку старым binary. Неподдерживаемая кнопка отсутствует или явно disabled; capability не имитируется через опасный fallback.

**PROTO-03.** Отдельные команды: ответ на вопрос, tool approval, permission expansion, MCP elicitation, steer активного turn и сообщение следующему turn. Adapter хранит native identity и явно описывает mapping. Для Codex turn/steer не позволяет менять model/sandbox; смена профиля проходит на проверенной границе, а не через текст сообщения. [S4]

**PROTO-04.** Request связан с project/run/stage/attempt, engine/adapter, runner generation, connection generation, native session/turn/item/request identity. Request ID локален своему transport. Ни смена движка, ни reconnect не делают старый ID валидным автоматически.

**PROTO-05.** До показа approval adapter обязан подтвердить, что native операция действительно ожидает решения и ещё не выполнена. Сохраняются безопасный preview, нормализованный payload, hash, TTL и допустимые ответы. Human decision долговечен; «applied» требует native acknowledgment/readback. UNKNOWN delivery не ведёт к повторному разрешению вслепую.

**PROTO-06.** Для interactive wait сохраняется управляемая сессия; операторский timeout не равен model silence timeout. TTL приводит к deny/hold, не auto-approve. Движок без безопасного interactive wait допускается только в профили, где это не требуется и опасные действия запрещены.

**PROTO-07.** После смерти native engine pending transport requests становятся недействительными. История решения остаётся evidence. Resume означает только проверенные возможности данного движка; не обещается восстановление старого shell, HTTP-запроса или незавершённого approval RPC.

**PROTO-08.** После crash или смены движка сначала readback workspace, exact SHA/dirty state, PR и внешних effects. Сомнение ведёт в recovery_required. Междвижковая передача — handoff с новым контекстом/attempt по ENG-08, а не конверсия скрытой истории или credentials.

**PROTO-09.** Deny policy имеет приоритет. Разрешение человеком не выдаёт broad root/network/credential scope. Движок, который сам автоматически одобряет или отклоняет запрос до нашего UI, не засчитывается как полноценная реализация интерактивных подтверждений.

**PROTO-10.** Scoped merge/staging/deploy входят в MVP. Их выполняет доверенный release-компонент по exact target/artifact, server-side policy и ранее выданной делегации; повторный approval человека не требуется в её границах. Для изменения границ требуется отдельное решение. GitHub merge запускает штатный Coolify webhook. Независимый readback обязателен. Агент не получает Docker socket, произвольный root, широкие GitHub/Coolify credentials или право подписывать свой CI-result.

## 9. Авторизация и безопасность

### 9.1. Идентификация и роли

**AUTH-01.** Вход только через существующий Authentik: confidential OIDC Authorization Code + PKCE, server-side session, запрет открытой регистрации. Отдельное application/provider для Symphony Control; exact issuer/discovery/JWKS читаются из действующей конфигурации. Account identity — issuer + subject, не email. Проверяются signature, issuer, audience, expiry, state, nonce и exact redirect URI. [S7, S9, S10]

**AUTH-02.** Cookie — Secure, HttpOnly и подходящий SameSite; сессия не хранит credential в URL или localStorage. CSRF-защита обязательна для mutations; WebSocket/LiveView проверяют origin, session и права при событиях.

**AUTH-03.** Роли по проекту: Viewer — чтение; Contributor — создание/редактирование карточек и обсуждение в разрешённых переходах без agent enqueue/approve; Operator — admission/сообщения/runtime lifecycle; Approver — permitted requests; Project Admin — конфигурация/участники/интеграции в пределах platform policy. Platform Admin управляет ресурсами/global stop; чтение карточек требует explicit membership. Роли можно совмещать явно. Agent identity получает только scoped service capabilities, не человеческую роль.

**AUTH-04.** MFA для Admin/Approver через существующие возможности Authentik; чувствительные действия требуют свежего подтверждения не старше 5 минут. Не менять глобальный flow других приложений ради этого. Один владелец может иметь несколько ролей, но это не независимое двухстороннее согласование. Revocation закрывает действующие UI/API/live permissions не позднее 60 секунд.

**AUTH-05.** Один OIDC client на web-продукт, а не по client на каждый проект. Базовые scopes: openid/profile/email; project roles задаются локальными memberships или точным allowlisted group-to-role mapping. Неизвестная группа не даёт никаких прав. Признак superuser в IdP не становится автоматически Platform Admin. goauthentik.io/api для обычного входа запрещён; offline_access добавляется только при обоснованном session design. [S7]

**AUTH-06.** Group mappings и membership source фиксируются в ADR. Удаление локальной роли, исключение из разрешённой группы и деактивация пользователя в Authentik тестируются отдельно. Истёкшее/неподтверждённое право не принимается из старого JWT; при отсутствии свежей авторизации mutations закрываются.

**AUTH-07.** Проверяются RP-initiated logout, подписанный back-channel logout и актуальность permissions на точной установленной версии. Back-channel требует реализации на стороне приложения; его наличие не доказывает событие при каждом изменении группы. Механизм контроля membership/session freshness с верхней границей 60 секунд утверждается в M0 без широкого admin-token; до фактического AC-22 соответствие не заявляется. [S8]

**AUTH-08.** При недоступности Authentik нет fallback на пароль/Basic Auth и auto-approve. Новые входы и неподтверждённые команды отклоняются; уже разрешённая самостоятельная работа runner может продолжаться в пределах собственной policy. Выход пользователя из браузера сам по себе не является командой остановки его проектов.

**AUTH-09.** Права на принятие результата задачи (issue.review_accept/close) отделены от права protocol approval. По умолчанию итоговую приёмку агентной задачи выполняет Project Admin либо явно назначенный reviewer с этим действием; агент не принимает собственную работу. Contributor сохраняет обычные разрешённые переходы ручных задач. Делегирование перечисляет конкретные действия, а не скрыто расширяет все права роли.

### 9.2. Секреты и границы исполнения

**SEC-01.** Секреты не размещаются в git, image layers, build args, issue, workflow, argv, UI, audit payload, logs или артефактах. Используются runtime secret references и независимые identities нового проекта. Существующие credentials DF Assistant не копируются.

**SEC-02.** Раздельные полномочия для model auth, native tracker tools, GitHub publication, runner transport, DB и инфраструктуры. Agent child не наследует управляющие переменные окружения. Одного удаления env недостаточно: проверяются UID, filesystem mounts, /proc, metadata service и доступ к локальным sockets.

**SEC-03.** Git-доступ ограничен repository bindings конкретного нового проекта. Repo-scoped read credentials не разделяются с другими runner; публикация write проходит через project/operation-aware boundary из SEC-04. Для API — минимально scoped GitHub App или утверждённый short-lived механизм. Общий постоянный широкий PAT и копирование credentials текущего DF Assistant запрещены.

**SEC-04.** Изменения native tracker и Git/PR publication проходят через project/operation-aware domain endpoints/broker. Agent не получает DB credentials, raw SQL/GraphQL или универсальный tracker admin token. Project/task/attempt/epoch извлекаются из доверенного назначения, не из аргумента модели; старый fencing epoch не выполняет mutation. UI и tools используют одинаковые ограничения, но разные actor capabilities.

**SEC-05.** Runner не получает root/sudo/Docker socket, host filesystem, host network или публичный control port. Базовые контейнерные ограничения: non-root, drop capabilities, no-new-privileges, контролируемые writable mounts, ресурсные лимиты и совместимый sandbox. Docker daemon относится к привилегированному control surface, не к инструментам worker. [S11]

**SEC-06.** Доступ runner к production DF Assistant, несогласованным внутренним сервисам, metadata endpoints и несогласованным RFC1918/link-local назначениям запрещён. Egress ограничивается необходимыми провайдерами. Настройка новых proxy/endpoint требует административного validation против SSRF.

**SEC-07.** Issue, комментарии, README, tool outputs и артефакты считаются недоверенными. Они не меняют security policy, allowlist, роли, credential scope, runner image или правила release. Shell hooks из workflow — исполняемый код и требуют review как код.

**SEC-08.** Secrets redaction применяется до долговечного event/log storage; при наличии несанитизированного payload он не публикуется. Тестируются multiline/control-character ошибки, заголовки, query params, diff, zip/artifact traversal и malicious Markdown.

**SEC-09.** Браузер получает безопасный preview, а не authentication tokens, transport receipts или signed URLs. Внутренние секретные идентификаторы отделены от непривилегированных correlation IDs.

**SEC-10.** Разделение project_id проверяется как security boundary на чтении, записи, очередях, tools, secrets, artifacts и export. Межпроектные negative tests обязательны. Authentik user/session не передаётся агенту как универсальный credential.

## 10. Workflow, native tracker adapter и GitHub

**WF-01.** У каждого проекта собственный workflow draft/version/history. До активации выполняются schema/template validation, diff, security policy validation и preview admission только этого проекта. Версия immutable и имеет hash. Каждый run pin-ит project/workflow/policy; активация A не меняет B.

**WF-02.** Изменения модели, sandbox, hooks, сети, concurrency и repo binding не изменяют активный run молча. Policy revoke действует немедленно как safety restriction; расширение прав — только для отдельно принятого нового контекста.

**WF-03.** Secrets задаются references, не значениями. Интерполяция не должна давать агенту read доступа к окружению control или произвольным файлам. Бизнес-приоритет карточки не расширяет технический scope.

**INT-01.** Форк реализует native Tracker adapter поверх нашего Tracker domain: чтение eligible issues, refresh states и нормализация устойчивых IDs/категорий без внешнего HTTP к Linear. Proposed kind = native — новый контракт форка, не утверждение о готовой опции upstream. Default provider — native; отсутствие Linear token/SDK/service не мешает boot/readiness. У control нет второго независимого tracker scheduler. Место подключения проверяется на exact upstream revision. [S15]

**INT-02.** Native tools для агента: issue_get/context, issue_search в разрешённом scope, workpad_upsert, comment_add/evidence_attach, issue_create_draft и request_review. Exact names/schema утверждаются и тестируются; это не совместимость с linear_graphql. Запись идёт через domain policy/transaction/outbox; retry не дублирует workpad или комментарий. В карточке сохраняются accepted scope, issue revision, branch/base, результаты, blockers и ссылки на attempts.

**INT-03.** Git flow: fresh fetch → exact base → isolated workspace/branch → tests → related commit → non-force push → PR → checks exact HEAD → review. Агент не пишет в protected release branch.

**INT-04.** Из UI можно читать diff, проверки и review и вернуть задачу на доработку с инструкцией. PR creation, review acceptance, merge и deployment учитываются как отдельные provider operations.

**INT-05.** CI-provider не назначается автоматически. До релиза выбирается разрешённый CI path; GitHub Actions не включаются без отдельного решения. Обязательный проверяемый статус привязан к exact PR HEAD; отсутствие сигнала — gap, не pass.

**INT-06.** При webhook-поддержке проверяются подпись, источник, payload limits и replay. Fresh provider readback подтверждает итог; webhook не является единственным доказательством состояния.

**INT-07.** Разбудить scheduler можно committed outbox event; periodic reconciliation остаётся страховкой. Состояние business issue не вычисляется парсингом agent output, webhook или логов. При недоступности Tracker domain/БД новый admission fail-closed, существующий runner следует REL-04. Native domain transaction имеет readback; распределённого «записали в наш UI, потом когда-нибудь в Linear» нет.

**INT-08.** Чистый production profile стартует без Linear secrets и без доступа к linear.app/api.linear.app. Операционный путь не содержит linear_graphql, Linear GraphQL schema, required external project slug и callbacks Linear. Исходные upstream files/неактивный adapter могут сохраняться для истории, но не загружаются обязательной зависимостью и не создают outbound telemetry. Opt-in импорт — отдельная операция, не live sync и не fallback.

**INT-09.** Полная потеря model/Git API не препятствует локальному созданию/редактированию/поиску/комментированию задач при исправных core/DB/Authentik. В карточках выполнения честно видна недоступная внешняя зависимость. Возобновление внешнего API не запускает все задачи автоматически без проверки policy, versions и limits.

## 11. Надёжность и повторные операции

**REL-01.** Не обещать универсальный exactly-once для внешних сервисов. Внутри системы используются durable intent, idempotency и fencing; снаружи — provider idempotency либо deterministic identity + authoritative readback.

**REL-02.** Перед внешним Git push/PR write сохраняются intent/exact target; после timeout выполняется authoritative readback или unknown без blind retry. Native tracker mutation фиксируется локально одной транзакцией с idempotency key; при потере ответа повтор возвращает зарегистрированный результат, а не создаёт новую issue/comment. Это не обещает exactly-once для внешних провайдеров.

**REL-03.** Повторы только для классифицированных transient failures: exponential backoff с jitter, учёт Retry-After, лимит попыток и circuit breaker. Auth, schema, policy и approval errors не лечатся бесконечным retry.

**REL-04.** Потеря DB запрещает новые claims, approvals и публикацию. Runner перестаёт принимать новые команды; по истечении bounded grace останавливает активный turn. Интерфейс честно показывает деградацию. Последующие действия восстанавливаются через reconciliation.

**REL-05.** Мгновенная остановка стороннего HTTP-запроса или rollback уже выполненного Git push не гарантируются. Итоги safety stop включают завершённые, остановленные и неизвестные побочные эффекты.

**REL-06.** После рестарта сохраняются pause/emergency state, решения человека, попытки, timeline, known provider operations и незавершённые вопросы как evidence. Новая рабочая сессия не наследует автоматически старое разрешение.

**REL-07.** Disk pressure закрывает admission до исчерпания места; невозможность durable записи не маскируется успешным приёмом команды. Очистка не удаляет dirty workspace, pending review или evidence незавершённой операции.

**REL-08.** Начальные настраиваемые таймауты для приёмки: heartbeat 5 секунд, lease 30 секунд, soft interrupt 30 секунд, ожидание подтверждения forced stop 15 секунд. Эти интервалы не разрешают новый запуск без доказанного прекращения прежнего. TTL approval по умолчанию 30 минут; истечение приводит к deny/hold, а не к разрешению. Значения фиксируются в policy и проверяются fault tests.


## 12. API и наблюдаемость

### 12.1. Предлагаемый API

**API-01.** Версионированный control API, не upstream endpoints: GET/POST /api/v1/projects; GET/PATCH /api/v1/projects/{project_id}; GET /api/v1/projects/{project_id}/runs; GET /api/v1/runs/{id} и /events; POST /api/v1/projects/{project_id}/commands; POST /api/v1/runs/{id}/commands; POST /api/v1/requests/{id}/decision; GET /api/v1/commands/{id}. Глобальные команды вынесены в /api/v1/platform/commands с отдельным RBAC.

**API-02.** Команда передаёт тип, expected_version, idempotency_key, reason и ограниченный payload. Server-derived actor/role нельзя переопределить полями запроса. Ответ содержит безопасный correlation ID и accepted/applied/rejected/unknown.

**API-03.** Ошибки типизированы: forbidden, scope_mismatch, stale_version, stale_request, unsupported_capability, runner_unavailable, policy_denied, provider_outcome_unknown. Отсутствует silent success или fallback на shell.

**API-04.** Web/API и LiveView используют одинаковые RBAC/domain services. Health endpoint наружу содержит минимум данных; подробные build/config/runner данные защищены авторизацией.

**API-05.** Native tracker API: /api/v1/projects/{project_id}/issues; /issues/{id}; /issues/{id}/comments, /relations, /activity, /execution-requests; project /status-schemes, /cycles, /milestones, /views, /documents, /exports и /imports. Список/поиск имеют cursor pagination и max page size; запись — expected_version/idempotency. Attachment bytes выдаются через авторизованный endpoint, не по публичному пути.

**API-06.** Machine tools — ограниченная проекция Tracker domain API с серверным assignment context. Human OIDC session не передаётся runner. Сервисная identity не может через общий REST расширить свою tool capability. HTTP/API ответы и live events используют те же permission checks, revision IDs и redaction.

**API-07.** Новые типы ошибок: invalid_transition, dependency_cycle, dependency_unresolved, admission_required, task_revision_conflict, attachment_quarantined, import_conflict. Validation error не превращается в auto-correction пользовательского scope. Read-only web/API имеют лимиты запросов; API документация доступна локально и не требует стороннего портала.


**API-08.** Версионированные endpoints для agent/model registry, routing preview/decision, budget reservation/status, handoff и device subscriptions. Agent/operator не может изменять registry/pricing/platform policies без соответствующей роли. Proposed paths: /api/v1/agent-profiles, /model-profiles, /projects/{id}/routing-preview, /runs/{id}/handoffs, /projects/{id}/budget, /me/devices. Имена — контракт будущей реализации.

### 12.2. Сигналы эксплуатации

**OBS-01.** Раздельные сигналы: liveness core, tracker read/write readiness, DB/storage readiness, runner availability и project admission readiness. Отказ модели/Git не означает недоступность локального tracker и не вызывает restart storm. БД недоступна — нельзя показывать сохранённую карточку как свежую authoritative запись.

**OBS-02.** Метрики отдельно по platform/project/runner и совместно используемому quota pool: queue age, active/waiting counts, request age, heartbeat lag, lease conflicts, command latency/outcome, unknown writes, provider errors, event/outbox lag, auth failures, disk, token usage, reserved/estimated/reconciled cost, routing outcomes и backup age. Сводный здоровый статус не скрывает неисправный проект.

**OBS-03.** Классификация инцидентов: target-system defect, protocol/MCP defect, schema mismatch, permissions issue, unavailable dependency, missing capability. Для unknown указываются недостающий сигнал и способ его получения.

**OBS-04.** Tokens берутся из provider/runtime evidence. Стоимость показывается как estimate с версией тарифов, currency и timestamp; при неизвестной цене — UNKNOWN, а не ноль. Выставленный счёт и оценка расхода не смешиваются.

**OBS-05.** Обязательные локальные уведомления: assignment/mention, waiting input/approval, failed/recovery_required, ready for review и emergency stop. Inbox, delivery history и read/ack находятся в нашей БД. Внешний канал — opt-in по отдельной настройке, например существующий SMTP; его отсутствие не делает систему зависимой от SaaS. Для включённого канала требуется отдельное доказательство доставки. Закрытый браузер не называется фактическим получением live-уведомления; уведомление сохраняется до следующего входа.

## 13. Deployment, хранение и rollback

**OPS-01.** Независимые dev/test/prod конфигурации внутри существующего Coolify. Новый core и runner-ресурсы не используют application, DB/volumes и identities DF Assistant. Использование общего Coolify или IdP не даёт доступа к другим production-сервисам. Хост для workload выбирается по fresh capacity/security readback; новый хост не заказывается автоматически.

**OPS-02.** Images, зависимости и совместимость pinned; latest запрещён в release manifest. Manifest фиксирует fork SHA, upstream SHA, image digests, engine/adapter versions, protocol schemas, catalog/routing policy versions, DB migration и workflow/policy hash.

**OPS-03.** Build/test выполняются в изолированной среде, не на runtime с production secrets. Fork сохраняет upstream history, LICENSE и NOTICE; обновления upstream идут отдельными PR с контрактными regression tests.

**OPS-04.** Compose публикует только разрешённый web origin через TLS edge. PostgreSQL и runner доступны только внутри private network. Проверяются bind addresses, firewall, DNS/TLS, websocket routing, uid/gid ownership, persistence, restart/boot и exposure с внешней точки.

**OPS-05.** Workspace, engine-specific state (включая CODEX_HOME для Codex) и артефакты сохраняются вне writable image layer в отдельных project volumes/bind mounts Coolify. Storage identity привязана к project/slot; чужой volume нельзя подставить через UI. Volume не является backup. [S6]

**OPS-06.** Единственный release path каждого ресурса: PR → обязательные checks exact HEAD и независимый review → автоматическая server-side проверка делегации/квоты → merge exact HEAD → штатный GitHub→Coolify webhook → readback exact image/commit/config → functional acceptance. Preview/staging до release выполняется там, где это предусмотрено risk profile; повторный ручной release approval в границах делегации не нужен. Одинаковый repo не означает fan-out deploy всех runner при каждом merge: resource-specific watched paths/release refs должны быть явно настроены и проверены. Если установленный Coolify не даёт нужного разделения, используются отдельные конфигурационные release refs, без ручного parallel deploy.

**OPS-07.** При обновлении runner A выполняются drain/reconciliation только A; B сохраняет свой процесс и attempts. Обновление общего core/DB — отдельное общесистемное maintenance с protocol compatibility и readback всех проектов. Нельзя маскировать его как независимое обновление runner. Процессы не дублируются независимо от deploy strategy.

**OPS-08.** DB migrations — expand/contract; перед destructive change отдельное решение и backup. Откат приложения возможен только при совместимой схеме. Если старый код несовместим, объявляется forward-fix/restore plan, а не фиктивная кнопка rollback.

**OPS-09.** Backup зашифрован, вне того же failure domain, с отдельными правами. Включает native issues/revisions/relations, comments/docs, memberships/config, execution state и bytes вложений/artifacts с manifest/hash. Restore проверяет согласованность metadata и файлов; поиск пересоздаётся локально. Admission закрыт: внешние PR/пуши могли сохраниться при откате БД. Старые session tokens, leases и RPC approvals не оживляются как действующие полномочия.

**OPS-10.** Retention для согласования: задачи, комментарии, их revisions/история, документы и ссылки на evidence сохраняются до явного archive/purge; закрытие задачи не удаляет их. Security audit — 180 дней, sanitised run event bodies — 30, крупные run artifacts — 14, clean workspace — 7 дней после review. Удаляемые bytes оставляют metadata/hash/tombstone; нужное acceptance evidence закрепляется hold. Dirty/active/unknown/pending-review защищены; project quota не удаляет tracker историю молча.

**OPS-11.** Манифест ресурсов хранит Coolify UUID, desired/observed image digest, host/destination, project/slot identity, mounts, network, CPU/RAM/PIDs limits и protocol version. Проверяется фактически сгенерированный deployable Compose и runtime limits: существование параметра в исходном YAML не доказывает его enforcement. [S13]

**OPS-12.** Общие control/DB могут хранить project-scoped данные, но backup/restore/replay не должен смешивать проекты. Восстановление A не переписывает DB-состояние B через неограниченный restore в live DB; схема selective recovery требует отдельной процедуры. Full restore выполняется в isolated environment со всеми admission закрытыми.

Офлайн нет runtime writes/approvals. CPU/network profile фиксируются в mobile test report; p95 сервера из NFR-01 не выдаётся за мобильное LCP.

**NFR-14.** Два разных agent engines/провайдера проходят живой end-to-end сценарий собственных проектов. Registry показывает отдельно tested/experimental/unsupported и requested/observed model. Переключатель модели без реальной смены принятого профиля — FAIL.

**NFR-15.** Routing rules воспроизводимы на одном snapshot входов; missing compatibility/price/usage не превращается в успех/нулевую цену. Недоступность advisory-модели не блокирует ручной tracker и безопасный детерминированный routing разрешённого профиля.

Точный infrastructure/model budget и host sizing утверждаются после M0/M1 benchmark. До этого не обещаются стоимость, скорость разработки или завершение задач за фиксированное время. В MVP обязательно доступны лимиты turns, времени, токенов и concurrency; без достоверной цены денежный лимит не выдаётся за точный hard cap.

## 17. Результаты работ, управление изменениями и Definition of Done

### 17.1. Обязательные артефакты

Репозиторий форка с upstream history и реестром delta; архитектура/ADR/threat model; Dockerfile/Compose и nonsecret примеры конфигурации; версии схем и migrations; typed API/protocol contracts; автоматические unit/integration/contract/E2E/failure tests; CI evidence; runbooks start/stop/recovery/credentials/backup/restore/deploy/rollback; release manifest; acceptance report с exact SHA/digest и известными ограничениями.

Предлагаемые ADR: ADR-001 Coolify topology, ресурсы и независимый deploy; ADR-002 upstream/agent-adapter compatibility; ADR-003 существующий Authentik, project roles и revocation; ADR-004 runner isolation и publication boundary; ADR-005 durable state/fencing/recovery; ADR-006 approval semantics; ADR-007 retention/backup/budget; ADR-008 CI и protected branches; ADR-009 project isolation, scheduler fairness, shared quotas и onboarding; ADR-010 native tracker/data model/statuses/admission/tools; ADR-011 bootstrap/import/export/attachment storage и self-hosted dependency boundary; ADR-012 agent/model registry и handoff; ADR-013 routing/evaluation и spend enforcement; ADR-014 mobile PWA/push/offline threat model; ADR-015 quality evidence/context/role stages. Названия предлагаются для последующего репозитория, файлы ещё не созданы в GitHub.

### 17.2. Работа с backlog

До готовности native tracker definitions хранятся в planning/backlog.json. Для немодифицированного bootstrap Symphony используется поддерживаемый им GitHub Issues adapter только нового private repo. Git — источник утверждённых определений, GitHub issue — единственная временная execution-карточка с workpad/state и stable task_id; JSON не выдаётся за готовый upstream adapter. Только dependency-ready task получает метку допуска. В native tracker переносится definitions + execution history по описанной ниже процедуре; обязательный Linear не вводится. Создавать Linear-проект для начала работ не требуется. После готовности native adapter выполняются drain старой очереди, однократный idempotent import определений/комментариев/evidence, count/hash/relationship readback и cutover единственного scheduler owner. Старые GitHub execution-метки снимаются, mappings сохраняются, запись ведётся только в native tracker. Обновление утверждённых requirement definitions остаётся Git-reviewed; второй редактируемый execution backlog и двусторонняя синхронизация не создаются.

Новые существенные defects сначала проверяются на duplicate и регистрируются в журнале своего фактического владельца: для Symphony Control — bootstrap backlog, затем native tracker. Один root cause → одна основная issue. Связь requirements INV/DEC/ARCH/PRJ/TSK/DATA/ADM/STATE/SCH/CMD/PROTO/AUTH/SEC/WF/INT/REL/API/OBS/OPS/ENG/ROUT/BUD/EVAL/MOB/AUTO/CTX/QUAL/NFR/AC с тестами обязательна. Утверждение требований не мигрирует существующие Linear issues DF Assistant и не меняет правила его действующего процесса.

Начальная реализация самого форка выполняется одним назначенным исполнителем в отдельном writable workspace; дополнительных исполнителей этой разработки автоматически не запускаем. Это организационное ограничение текущей работы, не ограничение возможностей продукта: многопроектная параллельность обязательна в MVP. Изменения только feature branches/PR; direct push protected branch, force push и немедленное самообновление работающего bootstrap не являются штатным path. Delegated webhook release продукта выполняется независимым release-компонентом.

### 17.3. Definition of Done

Готово только при наличии принятого design baseline, реализованной agreed delta, прошедших mandatory tests, AC-34 без Linear, полноценных human tracker операций и двух параллельных проектов, exact revision, независимого runtime/readback и функционального acceptance нового deployment. Security invariants сохранены; rollback/restore проверены; отсутствует незарегистрированный существенный defect; delivery уведомлений и mobile acceptance доказаны; минимум два tested agent engines, routing и budget semantics проверены; проект DF Assistant продолжает жить независимо.

**Нельзя называть завершением:** создание форка; container running; HTTP 200; появление кнопок; synthetic test без live acceptance; merge без проверок exact SHA; сохранение approval в DB без доказательства допустимого выполнения; restart, после которого исчез blocked.

## 18. Агентные движки, модели и переносимость

### 18.1. Разделение сущностей

**ENG-01.** Отдельные объекты: agent engine (исполняющий цикл и native protocol), adapter (наша интеграция), model provider/account, model profile, role (planner/implementer/reviewer), runner (изолированная среда). Codex или Claude Code — движки, а не универсальные названия моделей. OpenAI-compatible HTTP не доказывает одинаковые tool use, approvals, resume или sandbox. Runtime agent loop остаётся локальным; hosted agent service не подменяет self-hosted runner.

**ENG-02.** Общий AgentAdapter contract: preflight/capabilities, start, stream_events, send_input, decide_request, interrupt, observe_exit, resume_if_supported, collect_usage, export_handoff. Конкретные native IDs сохраняются в typed envelope; unsupported возвращает явную ошибку. MCP предоставляет tools, а ACP может унифицировать часть client↔agent взаимодействия; оба не заменяют scheduler, persistence, security policy и тесты наших adapters. ACP используется только для реально поддерживающего его профиля. [S24]

**ENG-03.** Engine profile содержит точный binary/package version, image digest, adapter/schema version, лицензирование, method of auth, OS/sandbox compatibility, model allowlist, tool/permission capabilities, observed usage/cost provenance, ограничения и статус disabled/experimental/accepted/deprecated. Registry моделей хранится у нас, не зависит от внешнего каталога при каждом открытии UI. Discovery/обновления создают candidate snapshot; автоматическое подключение новой модели или исполняемого plugin запрещено.

### 18.2. Предлагаемые интеграции

| Движок | Основа интеграции | Объём первого выпуска и ограничения |
| --- | --- | --- |
| Codex | Native App Server: структурированные sessions/turns/events/approvals/model discovery | Первый обязательный adapter; exact version и profile проверяются, исторический pin не объявляется актуальным [S4] |
| Claude Code / Claude Agent SDK | Локальный Python/TypeScript SDK с agent loop, tools, permissions и sessions | Второй предлагаемый обязательный adapter; API/другой разрешённый auth, не копирование чужого consumer login; hosted Managed Agents не подмена [S20, S21] |
| OpenCode | Headless server/SDK, sessions, permissions, provider/model config | Следующий adapter для разных провайдеров/локальных моделей; API не публикуется, sharing выключен; acceptance отдельно [S22, S23] |
| Gemini CLI | Документированный headless JSON/stream-json | Следующий adapter; наличие событий не доказывает двусторонний approval/resume. Полный interactive профиль только после exact-version проверки [S25] |

Это порядок предложения, не уже установленное ПО и не окончательный рейтинг качества. Допускается изменить второй adapter отдельным ADR, но multi-engine acceptance нельзя заменить двумя моделями внутри единственного движка. Первые два accepted профиля должны поддерживать требуемые safe approvals/stop и собственные tools без обхода запретов. Не требуется создавать свой tool loop для каждого LLM API.

**ENG-04.** Каждая attempt pin-ит engine+adapter+model profile+effort+policy. Фиксируются requested identity, resolved catalog identity и observed served identity, если провайдер её сообщает. При alias без прозрачного snapshot точная версия модели UNKNOWN; нельзя приписывать ей вымышленный immutable ID. Модель выбирается только из поддерживаемых данным движком вариантов. Effort/длина контекста/инструменты — отдельные параметры, не общий «умный режим».

**ENG-05.** Operator pin, проектный default и автоматический выбор доступны раздельно. Operator pin сохраняется до явного изменения/expiry и не снимается fallback-логикой. Ни операторский override, ни рекомендующий LLM не могут разрешить engine/model, запрещённые platform policy, data policy, quota или обязательными capabilities. Перед запуском UI показывает весь resolved профиль и причину допуска/отказа.

**ENG-06.** Project runner может содержать заранее проверенные бинарники обоих движков, но supervisor запускает только назначенный. Для каждого engine/profile — отдельные HOME/session directories и process environment; выдаются только разрешённые текущему запуску credentials. Все доступы провайдеров не монтируются агенту «на будущее». Альтернативные project-bound runner images допустимы, но замена требует preprovisioned resource и безопасного drain, без Docker API у агента.

**ENG-07.** Строгое разделение supervisor и недоверенного agent child распространяется на каждый SDK. Встроенные subagents, авто-переключение моделей, external plugins и дополнительные sessions выключены, пока не доказаны visibility, project scope, concurrency accounting и spend accounting. Невозможно их учесть/ограничить — профиль не допускается к autonomous mode. Упаковка Python/TypeScript SDK в runner не требует переписать Elixir control.

**ENG-08.** Cross-engine handoff — новый stage/attempt, не импорт native session. Прежний процесс остановлен/изолирован и проверен; manifest содержит task revision, accepted plan, base/head/tree, branch, dirty diff/patch hash или явное отсутствие, environment/toolchain lock, tests/evidence, открытые вопросы и known external operations. Handoff не требует преждевременного push грязного кода. Отдельно хранятся факты и непроверенные гипотезы; секреты, approval receipts и скрытые рассуждения модели не переносятся.

**ENG-09.** Новый движок получает минимальный допустимый context snapshot; применяются новые credentials/data checks. Нет гарантии одинакового поведения или полного сохранения смысла native conversation. При неизвестном исходе внешней операции handoff блокируется. Native resume остаётся возможностью того же tested профиля и не считается переносимостью между поставщиками.

**ENG-10.** Обновление engine/SDK/schema — отдельный PR, replay redacted protocol fixtures, fault tests, sandbox live test, candidate routing evaluation и возможность возврата к прошлому approved profile. Профиль с регрессией выводится из нового admission; активная attempt не получает silent binary/model upgrade. Runtime preflight проверяет доступность tools/auth/model до затратного запуска.

## 19. Выбор агента/модели, затраты и проверка качества

### 19.1. Цель и режимы

Цель — уменьшать стоимость и время до принятого изменения при установленном минимуме качества и безопасности. Не оптимизировать число токенов, число закрытых карточек или self-reported confidence. Более дорогая модель может быть выгоднее, когда предотвращает повторную работу; низкая цена не означает автоматически низкое качество.

**ROUT-01.** Три режима: Manual (оператор pin-ит профиль), Recommend (система объясняет варианты, запуск после выбора), Auto (выбор из заранее разрешённых профилей в рамках policy). Режимы Economy/Balanced/Quality — настраиваемые предпочтения, не отдельные уровни полномочий. Автовыбор не подразумевает auto-approve и самостоятельный выпуск.

**ROUT-02.** Сначала hard filters: confidentiality/egress, engine capability, sandbox/tool access, язык/toolchain, context size, квоты/здоровье/accepted status и budget policy. Затем risk floor; только после него выбор допустимого cost/latency/quality профиля. Не найдено допустимых кандидатов — blocked с причиной, не попытка через несогласованный provider.

**ROUT-03.** Сложность и риск — разные признаки. Сложность: область изменений, зависимости, доказанное воспроизведение, определённость acceptance, качество тестов, новая технология и объём доступного контекста. Риск: auth/permissions, секреты, обработка данных, migrations, billing, production infrastructure. Однострочное изменение проверки прав может быть high-risk. Неизвестные признаки не считаются low-risk; консервативный профиль или triage.

| Пример класса | Предлагаемый маршрут | Обязательное условие |
| --- | --- | --- |
| Проверка формата, known static rule | Детерминированный инструмент без LLM, если достаточен | Результат проверяется тем же contract; не каждый шаг требует модель |
| Ограниченная low-risk правка/документация | Economy accepted profile | Ясные acceptance и targeted checks; executable workflow не классифицируется как безвредная документация |
| Обычная функция или воспроизводимый bug | Balanced профиль | Regression/targeted + relevant broader tests, scope limits |
| Архитектура, неизвестный root cause, сложный refactor | Quality analysis, затем подходящий implementer | Принятый план, budget ceiling, отдельный review |
| Auth/data migration/production boundary | Risk floor + human plan/review gate | Цена и small diff не снимают контроль; production write вне MVP |

**ROUT-04.** Первоначальный router — воспроизводимые versioned rules. Advisory LLM может предложить task classification/разбиение, но выдаёт structured recommendation без права исполнять, менять policy или утверждать факты. Его latency/usage входят в общий расход. При его недоступности доступны Manual и детерминированный разрешённый профиль; при неопределённом risk — hold, не дешёвый fallback.

**ROUT-05.** Decision record хранит входной snapshot, risk/complexity evidence, candidate set, исключения и причины, policy/catalog version, выбранный profile, оценку затрат/неопределённость и actor. На телефоне есть объяснение «почему этот агент/модель», без раскрытия private chain-of-thought. Не выдавать числовую вероятность успеха без калибровки на соответствующей выборке.

**ROUT-06.** Отдельные стадии analysis/plan/implement/test/review могут выбирать разные профили и engines. Планировщик один; роли не создают своих очередей. В первой версии стадии проекта выполняются последовательно в одном slot; два разных проекта параллельны. Unit tests/build не требуют model call. Для смены движка применяются ENG-08/09.

**ROUT-07.** Эскалация ограничена: предлагаемый default — не более двух repair cycles в исходном профиле и одной смены профиля/движка, всё в пределах общего task budget. Ошибка auth/permissions/schema/tool availability не лечится более дорогой моделью. Если scope/risk меняются — заново gate. Повтор того же error signature без нового evidence приводит к hold и точному вопросу.

**ROUT-08.** Fallback только на заранее разрешённый профиль того же или более строгого trust/safety класса. Недоступность провайдера, quota и rate limit классифицируются отдельно от неудачного решения. Учёт Retry-After/backoff/circuit breaker общий по account pool. Не передавать закрытый код другому провайдеру без разрешения и не обходить service restrictions/схемы доступа.

**ROUT-09.** Изменение profile/effort между turns допустимо лишь при подтверждённой capability и безопасной границе. Нельзя применить к текущему turn новую цену/модель без записи. Requested alias, фактически полученный model и неучтённый subagent выявляются telemetry; отсутствие такого сигнала — explicit limitation и закрытый auto mode при строгом требовании.

### 19.2. Бюджеты и честный учёт

**BUD-01.** Лимиты: task/run/stage, project/day/month, provider account pool и вся платформа; отдельно retries, turns, tokens, wall-clock и approvals wait. Смена engine, новый run той же task или reviewer не сбрасывают task-level aggregate. Время ожидания человека не расходует токены само по себе, но удерживает ресурсы; показатели раздельны.

**BUD-02.** Usage ledger дедуплицирует события по provider/request/attempt identity; cumulative snapshots не суммируются как deltas. Учитываются input/output, reasoning/cache semantics, tool/model fees, review и routing calls; нет двойного счёта reasoning, если он уже включён в output. Цена хранится с source/date/currency/model/region/billing mode и effective interval. SDK cost estimate не считается выставленным счётом. [S26, S27]

**BUD-03.** UI различает estimated, reserved, provider-reported и reconciled invoice cost; UNKNOWN не ноль. Subscription/quota profile не выдаётся за бесплатный API: хранятся способ доступа, quota/reset, отдельная аллокация подписки только с явно указанной формулой. Условия использования/право автоматизации проверяются по официальному источнику конкретного профиля; consumer subscription не считается универсальным credential. Для Claude Agent SDK документация отдельно ограничивает предложение сторонним пользователям claude.ai login/rate limits без предварительного разрешения. [S20]

**BUD-04.** Monetary hard cap — отдельная validated capability, а не checkbox по данным dashboard. Требуются своевременный accounting, атомарное reserve/reconcile для параллельных проектов и надёжное enforcement до каждого допускаемого billable request либо внешний provider cap с доказанной семантикой. Если CLI скрывает внутренние вызовы, SDK выдаёт только финальную оценку или цена неизвестна, показывается budget guard/estimate-only; строгий денежный профиль не допускается к unattended Auto. Лимиты turns/time/concurrency действуют независимо.

**BUD-05.** Новые requests прекращаются до порога с резервом под согласованную верхнюю оценку in-flight charges. Уже принятый провайдером запрос и поздно пришедшие начисления не отменяются нажатием Stop. Если worst-case charge нельзя ограничить, «никогда больше X» не обещается. Transport/credentials, позволяющие агенту обходить enforcement boundary, запрещены для strict-budget profile; общий LLM proxy не навязывается движку без проверки его совместимости.

**BUD-06.** Повышение budget — отдельная scoped команда с amount/currency/period/reason/expected_version и правами. При исчерпании лимита безопасный checkpoint/hold, уведомление и сохранение результата; никакой бесконечной доработки «ради завершения». Несовпадение usage/billing создаёт accounting alert, не автоматическую доплату.

**BUD-07.** Cost per accepted result = все относимые затраты выбранной когорты задач, включая failures, retries и review, делённые на число принятых результатов; отдельно success rate, rework/rollback rate, latency и число вмешательств. При нуле accepted показатель undefined, не ноль. Стоимость моделей, инфраструктуры и операторского времени показывается раздельно; цену времени человека не придумывать.

### 19.3. Локальная оценка и улучшение маршрутов

**EVAL-01.** Версионированный project-scoped набор репрезентативных задач: stack, risk, complexity, exact base/test fixtures и критерии. Минимум для пилота — 20 задач из не менее четырёх классов, включая unsafe/ambiguous случаи; такой объём проверяет механизм, но не доказывает универсальную оптимальность. Проекты/данные не отправляются провайдерам сверх их data scope.

**EVAL-02.** Сравнение с фиксированным Balanced baseline на одних задачах: accepted rate, defects/rework, elapsed/queue time, total spend и операторские решения. Учитываются неудачи/abort, размер выборки, доверие/неопределённость; результаты simple docs не обобщаются на security. Quality threshold утверждается до оценки. Human acceptance/независимые тесты важнее оценки модели самой себе.

**EVAL-03.** Новый router сначала shadow/recommend mode: сравнить решения без второго исполняющего агента и без двойной публикации. Offline replay измеряет только допустимые свойства; преимущество реального исполнения доказывается отдельным ограниченным canary. Production A/B с дублирующими writes запрещён.

**EVAL-04.** Регрессия качества, runaway spend или tool error rate отзывает новые automatic admissions данного профиля/маршрута. Переключение на прежнюю принятую policy сохраняет историю. Агент может предложить обновление rules/skills/prompts, но не менять свои полномочия или автоматически учиться на непроверенном успехе.

## 20. Управление с телефона

### 20.1. Mobile-first PWA

**MOB-01.** Одна self-hosted PWA поверх Phoenix UI/API, manifest/service worker/assets от нашего origin. Начальный экран «Требуют решения»; нижняя навигация: Внимание, Проекты, Запуски, Расходы. Доступны создание/редактирование задач, фото/файл как вложение, выбор engine/model/mode, enqueue, input, decision, stop и review. Не нужен отдельный native client для первой версии.

**MOB-02.** Карточка внимания показывает проект/задачу, что сделано, что подтверждено, что блокирует, точное требуемое решение, риск, время ожидания, budget и freshness. Не «агент завис» без причины. Большие логи/diffs — раскрываемые подробности; основной экран не требует чтения потока токенов. Автосводка помечается как summary и ссылается на исходные evidence.

**MOB-03.** Preview разрешения содержит конкретный target/action, изменяемые файлы/права, риск, scope, expiry и привязку к актуальному состоянию. Нет широкого approve-all, swipe-to-approve и одношагового разрешения из notification. Для рискованных действий — Authentik step-up согласно AUTH-04. Voice/text «да» в комментарии не считается разрешением.

**MOB-04.** Потеря сети показывает offline/stale и время последнего подтверждённого состояния. LiveView reconnect повторно читает server revision. Pending HTTP command проверяется по прежнему idempotency key; неизвестный ответ не создаёт новую команду. Offline runtime writes/approval очередь не сохраняется для автоматической отправки позднее.

**MOB-05.** По умолчанию service worker кэширует только публичную application shell, не private tracker/API/code/approvals. Локальный draft недоверенного текста допустим только opt-in с предупреждением и явной отправкой после reconnect; base version проверяется. Logout/revocation чистит пользовательский cache, прекращает subscriptions и не оставляет открытых данных другого пользователя.

### 20.2. Уведомления и доступ

**MOB-06.** Durable local inbox — источник уведомлений; Web Push — согласуемый транспорт доставки при закрытом UI, не новый источник задач. Generic payload без кода, секретов и чувствительного названия проекта; открытие deep link требует Authentik и свежего доступа. Subscription endpoints, приватный VAPID key и приватные delivery metadata не показываются пользователю и считаются секретными.

**MOB-07.** Mobile acceptance включает реальный закрытый/свёрнутый браузер, разрешение уведомлений, locked device, reconnect и expiry. Queued, handed-to-push-provider, opened и пользовательский ack — разные состояния; delivery receipt не выдумывается. На iOS Web Push Home Screen использует инфраструктуру Apple; следовательно, push transport не является полностью self-hosted даже при нашей БД и сервере. Для иных целевых браузеров ограничения фиксируются отдельно. [S28]

**MOB-08.** В первой версии поддерживаемый Web Push требует настройки владельцем; без разрешения канала панель работает, но unattended-mobile acceptance не заявляется. Opt-in SMTP/другой существующий канал может быть резервом. Отсутствие ack создаёт эскалацию по правилам, не auto-approve; quiet hours не отменяют emergency hold. Сообщения из Telegram/email не обходят authenticated UI.

**MOB-09.** Экран устройств/сессий показывает безопасные device labels и позволяет отозвать web session/push subscription; policy revoke действует и на старую вкладку. Права роли не хранятся только в мобильном клиенте. Биометрия/passkeys возможны через доступный согласованный Authentik flow, но не предполагаются настроенными. Lost-phone сценарий входит в tests.

**MOB-10.** Нельзя превращать обычные review/approvals в вынужденную работу на desktop. Доступны scoped diff, exact HEAD/checks, комментарий и ответ с телефона; сложный или oversized diff требует явного дополнительного review, не спрятанного auto-accept. Screen reader/клавиатура, contrast, text zoom и режим одной колонки входят в тесты. Ввод голосом через клавиатуру устройства допустим, но наш аудио-recording/transcription сервис — отдельная будущая функция с data policy.

## 21. Что делает оркестратор пригодным для автономной разработки

### 21.1. Полномочия и качество результата — первая версия

**AUTO-01.** Лестница делегирования: A0 — наблюдение/анализ; A1 — план/черновик; A2 — изменения, тесты и PR; A3 — scoped auto-release по делегации владельца. Для нового проекта A3 согласован без повторного approval обычных деплоев, но активируется только для exact repository/resource manifest и проверенных capabilities. Выбор Quality-модели и отсутствие оператора не расширяют полномочия. Агент не может сам повысить свой уровень.

**AUTO-02.** Допуск по определению готовности: цель, scope, acceptance, затрагиваемая revision/repo, available test plan, риск и бюджет. Неясная задача идёт в triage; агент предлагает проверяемые вопросы и декомпозицию. Разрешение deploy определяется действующей делегацией, а не самим текстом плана. Зависимости/subtasks представляют DAG; созданные агентом карточки не запускаются рекурсивно без admission.

**AUTO-03.** План стадий хранит inputs/outputs/критерии/роль/profile/limit. В MVP один writer и последовательный reviewer в проекте; reviewer работает на фиксированном snapshot и не имеет write/publish полномочий implementer. Другая модель может уменьшить общие ошибки, но не доказывает независимость и не заменяет human acceptance критичных изменений.

**AUTO-04.** Anti-loop: лимиты repair cycles/эскалаций, повтор одного error signature, отсутствие новых проверяемых evidence и внешние blockers. Тайминг/новый текст не считается прогрессом автоматически. Диагностика отличает code defect от missing credentials, flaky environment и broken MCP; плохой инструмент не компенсируется расходами более сильной модели.

**QUAL-01.** Acceptance evidence привязывается к exact HEAD/tree/base, test commands/exit codes, test suite version и runner image. Изменившийся HEAD аннулирует прежнее соответствие проверки. Само «тесты зелёные» из agent message — не проверка. Добавление regression test не разрешает удалить/ослабить остальные тесты ради PASS.

**QUAL-02.** Diff limit/risk classifier выделяет auth/migration/dependency/lockfile/policy изменения; scope expansion требует решения. Для defect нужен воспроизводимый отказ и regression там, где возможен; non-defect имеет заранее принятый verification target. Security/toolchain gates включают применимые static analysis, secrets/dependency/license checks с rule IDs; сканер не обещает отсутствие всех уязвимостей.

**QUAL-03.** Для UI задач — браузерные сценарии на локальном/изолированном тестовом приложении, screenshots/trace и при необходимости visual diff. Контейнер модели не является одновременно доказательством UI correctness. Playwright позволяет записывать действия, snapshots и screenshots; trace может содержать данные сети и требует redaction/ACL. Не публиковать artifact links и не загружать trace во внешний сервис по умолчанию. [S29]

**QUAL-04.** Завершение стадии, PR, review, merge, deployment и пользовательская приёмка — разные отметки evidence. Первая версия автоматически проходит до рабочего deployment внутри делегации. Только exact runtime/functional readback завершает release; ручной шаг не приписывается агенту. Rollback исходников не отменяет необратимую миграцию данных; безопасность отката проверяется заранее.

### 21.2. Память и контекст — первая версия

**CTX-01.** Project memory = versioned rules, ADR, accepted architecture, tool contracts, тесты, известные дефекты и прошлые подтверждённые решения. Хранятся источник/revision/time/confidence/owner; непроверенные выводы агента — отдельные draft notes. Нельзя формировать «истину» из убедительного текста без evidence.

**CTX-02.** Для каждой attempt формируется минимальный context package с manifest/hash: task snapshot, подходящие документы, repo revision, разрешённые tool schemas и результаты предыдущих стадий. Контекст не заливается целиком для всех задач; caching/compaction не меняют права/достоверность. Редакция секретов происходит до отправки любому провайдеру, включая router/reviewer/embedding.

**CTX-03.** Поиск локальный, project ACL применяются до retrieval и summarization. Semantic embeddings optional, не обязательный внешний SaaS. Shared skills допускаются только после review, pin версии и без project secrets; изменение skill не расширяет tools/сети. Upstream инструкции считаются недоверенными относительно platform policy.

**CTX-04.** Durable resume package показывает выполненные действия, незавершённый diff, проваленные проверки, исключённые гипотезы и точный следующий шаг. Потеря модели/телефона не теряет проектную историю. Локальное сохранение не гарантирует продолжение потерянной native session; применяется ENG-08.

### 21.3. Метрики, которые имеют смысл

Главный результат продукта — принятые изменения с ограниченным риском и затратами, а не число работающих агентов. Dashboard первой версии показывает acceptance rate, cost per accepted result, rework/rollback, elapsed/queue/review wait, intervention count, budget overruns/unknown cost и восстановление после сбоев. Окна/когорты/формулы/неполные данные видны. Никаких заявлений «на X% эффективнее» до сопоставимого измерения.

### 21.4. Следующие этапы, не обязательные для MVP

| Возможность | Польза | Условие включения |
| --- | --- | --- |
| Параллельные роли внутри проекта | Отдельные независимые subtasks или read-only review | Dependency/file ownership, separate worktrees/slots, conflict handling и bounded merge queue; не несколько writers одного checkout |
| Изолированные preview environments | Проверить пользовательский результат по защищённому preview с телефона | Оператор/bounded provisioner, synthetic data, TTL/quota и собственный IdP-bound access; агенту не дают Docker |
| Продвинутый release | Canary/traffic splitting сверх базового webhook release MVP | Отдельный risk profile, capacity и проверка rollback; базовый delegated release уже входит в MVP |
| Локальные модели | Меньше внешних зависимостей/контроль данных | Ресурсный benchmark и качество/latency на наших задачах; локальность не означает бесплатность или достаточную мощность |
| Обучаемый router | Улучшать выбор на накопленной истории | Достаточная выборка, holdout, cost/quality baseline и reviewed promotion; не непрозрачный self-learning в production |
| Регулярные maintenance задачи | Выполнять повторяемые работы | Native scheduling/admission, dedupe/budgets; цель → ТЗ → DAG уже входит в основной сценарий MVP |

Предлагаемый приоритет: сначала доказать надёжность двух движков, native tracker, ограниченное Auto и телефон. Затем расширять adapters и локальные модели. Массовый swarm, публичный marketplace plugins, Kubernetes и свой LLM proxy не добавляются просто ради «самого лучшего» продукта.



## 22. Идея в ChatGPT → проект → автономная поставка

**FLOW-01. Основной сценарий.** Заказчик в облачном ChatGPT голосом или текстом описывает приложение: сервис, бот, MCP-сервер либо веб-продукт для Ubuntu/Coolify. Диалог уточняет пользователей, данные, интеграции, сценарии, ограничения и критерии. Результат — versioned specification, а не сразу произвольный prompt исполнителю. Встроенный web tracker остаётся полноценным альтернативным входом.

**FLOW-02. Входная готовность.** Перед самостоятельной разработкой фиксируются цель, границы, non-goals, внешние контракты, риски, test fixtures, definition of done, модель данных, допустимые публикации, бюджеты и delegation. Не нужно спрашивать известное из authoritative sources. Нерешённые технические факты устанавливает preflight; только решения владельца, не выводимые из доступных данных, возвращаются человеку.

**FLOW-03. Human effort.** Основное участие владельца — уточнение и принятие ТЗ, предоставление законной авторизации, решения вне delegated scope и итоговая продуктовая приёмка. Обычные code/test/review/deploy шаги не требуют повторного «продолжай». Недоступный внешний write, отказ permissions и превышение бюджета не обходятся от имени человека.

**FLOW-04. Состояния спецификации.** draft → clarified → accepted → superseded; отдельные requirement IDs/revisions, авторы, sources и change log. Для выполнения выбирается immutable accepted snapshot + hash. Изменение цели, security invariants либо бюджета создаёт новую ревизию и пересчитывает затронутый DAG; уже работающий turn не получает подменённый контекст.

**MCP-01. Собственный канал.** Новый продукт предоставляет remote MCP поверх поддерживаемого HTTPS-транспорта и тот же domain service layer, что UI/API. Установка соединения в ChatGPT и ограничения конкретного voice/client режима проверяются отдельным end-to-end сценарием. Наличие MCP endpoint не доказывает, что текущий ChatGPT сможет вызывать write из любого голосового режима. Web-панель доступна независимо.

**MCP-02. Identity.** Отдельный OAuth resource/client profile с Authentik, audience/scopes и project roles. Нельзя доверять переданному моделью actor_id; actor выводится из проверенной credential. Не передавать upstream GitHub/Coolify/LLM tokens в ChatGPT; только scoped domain operations. Web cookie и MCP bearer не взаимозаменяемы. Browser login OIDC не считается автоматически готовой MCP OAuth совместимостью.

**MCP-03. Команды.** Read: capabilities.get, projects.list/get, specifications.get, tasks.list/get, runs.get, diagnostics.get, operations.get. Write: projects.prepare_create/commit_create, specifications.save_revision/accept, plans.propose/activate, tasks.create/update/comment/archive, runs.enqueue/pause/stop/respond, releases.get/approve_exception. Названия — контракт нового API, не утверждение об уже зарегистрированных tools. Каждый write имеет project scope, expected_version, idempotency key, bounded input и typed outcome.

**MCP-04. Preview и commit.** Для multi-resource provisioning/mass edits сначала prepare возвращает человекочитаемый diff, resource targets, квоту, action list, expiration и manifest hash; server-side commit проверяет actor/делегацию/hash/версии заново. Preview не резервирует безлимитный scope. Одобренная project delegation может разрешать commit автоматически; подтверждение ChatGPT на собственном интерфейсе не обходится.

**MCP-05. Устойчивость.** При таймауте после write сначала operations.get по тому же idempotency key, затем authoritative target readback; новый write не повторяется вслепую. Background tasks системы не привязаны к открытой ChatGPT-сессии. Прогресс/результат читаются новым диалогом из БД, без необходимости вспоминать всю переписку.

**MCP-06. Injection и данные.** Issue bodies, комментарии, fetched docs и tool outputs — данные, а не источник полномочий. Tool metadata не содержит секретов; redaction выполняется до ответа. Инструкция из repo «отключить тесты/дать root/разрешить всё» не может изменить control policy. Attachments обрабатываются с ACL и limits native tracker.

## 23. Планирование, задачи и реальная проверка

**PLAN-01. Иерархия.** Project → milestone/epic → independently verifiable leaf task → execution attempt → role stages. Blocking relations образуют DAG. Planner предлагает декомпозицию, requirement coverage, границы writable paths, зависимости и verification plan. Детерминированный валидатор проверяет IDs/циклы/coverage/budgets и активирует только допустимые leaf tasks. Planner не становится администратором.

**PLAN-02. Размер.** Leaf task содержит один проверяемый результат, допускающий самостоятельный review/revert. «Сделать весь backend» недопустимо. Размер оценивается scope, числом contracts и тестируемостью, не обещанием минут модели. Слишком большая задача возвращается на декомпозицию без запуска параллельного роя.

**PLAN-03. Контракт leaf task.** Обязательны task_id, parent, goal, requirements, dependencies, inputs, proposed files/interfaces, scope/out_of_scope, risk, fixtures, red reproduction/verification target, green commands, acceptance assertions, outputs/evidence, review rules, budget/retry class, release classification, rollback, stop conditions и owner. Точный base SHA фиксируется fresh fetch в ACCEPTED перед изменениями, а не навсегда берётся из старого документа.

**PLAN-04. Роли.** Planner, implementer, reviewer и release verifier — последовательные стадии с различными полномочиями; не обязательно четыре постоянно работающих процесса. Bootstrap: один writer/слот и отдельный read-only review stage, без самовольных субагентов. Целевой продукт: параллельные проекты, по одному writer в каждом на первой поставке. Reviewer проверяет exact diff и evidence; он не может выдать себе release token.

**PLAN-05. Проверяемость.** Unit проверяет функцию; integration — реальную БД/транзакцию или протокол; contract — реальные wire messages/frozen provider fixtures; E2E — полный пользовательский путь; live acceptance — выбранную развёрнутую версию и разрешённые внешние integration calls. Mock-only PASS не закрывает integration/live criterion. Для docs/config вместо бессмысленного модельного E2E нужны parser/schema/template/static checks и consistency tests.

**PLAN-06. Test data.** Версионированные synthetic fixtures не содержат production secrets или персональных данных. Для tracker: два проекта, несколько ролей, blocking/cancel/reopen случаи, файлы и комментарии. Для runner: timeout/partial response/duplicate event/unknown outcome. Для MCP: реальный tools/list + tools/call на sandbox server и запрещённый cross-project доступ. Для bot/service: локальный HTTPS/webhook fixture и наблюдаемое изменение состояния. Live write требует exact sandbox target и readback; тест не создаёт дубликаты при повторе.

**PLAN-07. Test integrity.** Приёмочный набор и policy pin принадлежат release/verification identity, не автору правки. Изменение тестов/fixtures/risk rules видно отдельным diff; нельзя удалить assert, отметить flaky или подменить runner evidence ради зелёного цвета. Независимый verifier перезапускает обязательные проверки exact HEAD. Артефакты фиксируют exit code, measured assertions, data/schema versions, source and image IDs.

**PLAN-08. Продвижение.** Task accepted только после её обязательных проверок. Milestone accepted после интеграционного теста состава, а не суммы заявлений задач. При reopen зависимости ещё не начатые dependents удерживаются; активные получают explicit reconciliation. Failed task не переводит весь проект в Done.

**PLAN-09. Coverage.** planning/backlog.json и planning/traceability.json — проверяемая связь requirements ↔ tasks ↔ AC ↔ evidence. Нет обязательного требования без owning task. Краткий milestone не является доказательством полноты. План можно уточнять в рамках scope через versioned proposal, не теряя IDs/history.

## 24. Автоматическое создание инфраструктуры и выпуск

**PROV-01. Манифест проекта.** Новая private GitHub repo, baseline/upstream provenance, protected release ref, CI check names/identity, Coolify project/environment/app IDs, Authentik application/client, DB/schema/roles, domains/ports/networks/volumes, quotas, Git/LLM/runner identities и rollback predecessor. Чужие IDs не подбираются эвристически. Имена не доказывают принадлежность: проверяются stable IDs/tags и owner bindings.

**PROV-02. Typed provisioner.** Создание ресурсов выполняется доверенным, ограниченным интерфейсом оператора/платформы, не shell агента. create_repository, create_coolify_project/app, create_oidc_client, provision_runner, bind_secret_ref и health_readback имеют whitelist полей, bounded target/quota, audit и idempotency. Нет execute arbitrary root/shell, wildcard project scope и Docker socket. Широкая bootstrap identity, если разово необходима, не остаётся у агента; revoke подтверждается.

**PROV-03. Частичный provisioning.** Шаги и наблюдаемые external IDs сохраняются до следующего действия. Таймаут → lookup/readback → resume того же manifest, не создание копии. Компенсация удаляет только созданные этой операцией пустые ресурсы с доказанной ownership; база с данными/общий provider/чужая сеть не удаляются автоматически. Ошибка создания ресурса не маскируется ручным неучтённым объектом.

**PROV-04. Существующая инфраструктура.** Coolify и Authentik используются повторно. Host preflight CPU/RAM/disk/ports/DNS/egress — read-only; Ubuntu/Coolify не означают отсутствие расхода ресурсов. Для bootstrap берётся верхний предел 2 CPU/4 GiB/256 PIDs и 30 минут на один pilot запуск как начальная защитная настройка, не утверждение о доступной ёмкости. Без capacity readback paid worker не активируется. Значения меняются владельцем политики, не моделью.

**DEP-01. Делегация.** Заказчик разрешил автоматические deploy внутри нового выделенного проекта без подтверждения каждого шага. Делегация ограничивает repo/ref/resource IDs, environment, domains, resource ceilings, allowed migrations, check policy и expiry/revocation. Права не выводятся из текста issue. Вне границ — hold и один конкретный запрос владельцу.

**DEP-02. Обычный путь.** Fresh exact source → isolated feature branch → red/green + broader checks → PR → independent review и check exact HEAD → compare-and-merge expected HEAD → GitHub push/webhook штатного Coolify → correlation deployment/commit → runtime image/config/schema readback → health и functional acceptance. Сам факт создания PR не гарантирует deploy: release запускается настроенным событием/веткой, обычно после merge. GitHub Actions в этом проекте не включаются; CI-исполнение/публикация защищённого статуса реализуются согласованным self-hosted путём.

**DEP-03. Trusted checks.** CI status exact HEAD публикует identity, недоступная writer. Отсутствие checks, pending/timeout и result другого SHA не считаются pass. Если remote CI ещё не provisioned, задача может дать локальный evidence и PR, но auto-merge gate BLOCKED. Это технический gap, а не отмена делегации владельца.

**DEP-04. Очередь release.** На один ресурс — один release owner. Результат старого deploy не принимает более новый commit; out-of-order webhook дедуплицируется и сверяется с desired ref. Изменение HEAD после review требует новых применимых checks. Watch paths/release refs исключают перезапуск проекта B при изменении A. Self-update управляющей системы выполняет внешний bootstrap/release verifier с проверенным predecessor, а не изменяемый самим обновлением процесс.

**DEP-05. Post-deploy.** Проверки: exact SHA/image digest, config/migration versions; liveness/readiness и реальные функции с synthetic fixture; TLS/Auth/ACL; data persistence и target ownership. UI shows releasing → verifying → deployed_accepted, либо rollback_pending/rolled_back/recovery_required. Зелёный Coolify deploy сам по себе не завершает задачу.

**DEP-06. Auto-rollback.** В границах делегации автоматически возвращается известный predecessor, только если доказана совместимость данных/схемы, артефакт доступен и target тот же. Предпочтительно bounded release/revert через согласованный Git/webhook path; direct rollback допускается только существующей типизированной emergency capability с readback и последующим выравниванием desired Git state. Не делать force-push. Revert источника — новый commit, не возврат времени базы.

**DEP-07. Необратимость.** Destructive migrations/data deletion/смена общей инфраструктуры без отдельно принятого плана запрещены. При несовместимости rollback система останавливает admission/опасные действия, сохраняет evidence и сообщает recovery_required. Восстановление backup без оценки потерянных новых данных не выполняется автоматически. Нельзя обещать универсальный автоматический откат любого изменения.

## 25. Диагностика, конечные повторы и безопасная остановка

**DIAG-01. Наблюдаемое событие.** Корреляция project/task/attempt/stage/operation; monotonic sequence и UTC timestamp; target type и разрешённый identifier; error family/code/status; latency; subprocess exit/signal; exact code/image/config; sanitized last-N logs; trace reference; предыдущие действия и их outcomes. Body ограничен размером и redaction policy; полный dump env/argv/auth headers/cookies запрещён.

**DIAG-02. Классификация.** transient_transport, rate_limit, auth/permission, invalid_input/schema, target_defect, agent_code_defect, quota/budget, resource_exhaustion, unknown_external_outcome, lost_owner/lease, operator_required. UNKNOWN — допустимый честный итог. Классификатор выводит evidence и rule ID; он не заявляет «упал сервер» только по одному timeout.

**DIAG-03. Network retry.** Для явно идемпотентного read/connection preflight исходный профиль: первая попытка t0, повтор не раньше +10 секунд, следующий не раньше +60 секунд от второго отказа; всего 3 попытки. Затем durable stopped_dependency и notification event. Добавляется bounded jitter при множестве проектов; time plan и счётчик сохраняются, рестарт их не сбрасывает. Это runtime timers нового продукта, не задания ChatGPT Automations.

**DIAG-04. Разные ошибки — разные правила.** 429 уважает Retry-After внутри общего deadline/budget; 401/403, revoked auth, schema mismatch и отказ policy не повторяются как network glitch. Connection timeout не ведёт к более дорогой модели. Потеря общей сети открывает circuit breaker затронутого dependency pool и не создаёт шквал retry всех проектов. Здоровые независимые проекты продолжают работу при сохранных общих сервисах.

**DIAG-05. Write ambiguity.** Timeout после PR/create/deploy/task mutation имеет unknown outcome. Прежде любого повторения — status lookup по stable operation key и authoritative target. Нет такого сигнала — hold, capability gap, не retry mutation. HTTP метод не является достаточным доказательством идемпотентности бизнес-операции.

**DIAG-06. Repair loop.** Для code defect собирается reproduction, гипотеза и результат. Начальный лимит: два repair cycles и одна контролируемая смена профиля внутри task budget. Повторная error signature без новой проверяемой информации завершает попытку как stopped_no_progress. Новая фраза модели не сбрасывает счётчик. Лимиты модели, dependency retry и release retry раздельны и входят в aggregate budget.

**DIAG-07. Остановка без человека.** При исчерпании retry/deadline/budget, потере control ownership, недостоверном outcome, revocation либо угрозе данным система сама прекращает выдачу новых работ/оплачиваемых запросов. Уже исполняющийся subprocess получает bounded interrupt, затем terminate/kill только своего process group/cgroup; результат проверяется. Если kill/readback недоступен, состояние unknown, слот не переиспользуется. Подтверждение на безопасную остановку не нужно.

**DIAG-08. Полный отказ связи.** Runner имеет local monotonic watchdog, ресурсные лимиты и локальный durable stop record. Отсутствие UI/DB/notification transport не разрешает бесконечную работу. При восстановлении он передаёт deferred evidence/outbox и сначала reconcile, а не автоматически продолжает потерянную задачу. Новая работа без lease/policy не начинается. Сетевой сбой не гарантирует остановку уже отправленного оплачиваемого запроса провайдера — это отдельно учитывается.

**DIAG-09. Сообщение владельцу.** Одна карточка инцидента: что выполнялось, где остановилось, точные sanitized codes, подтверждённые факты/гипотезы, использованные попытки, сохранённые outputs и минимальное необходимое решение. Нет доставки — notification_pending и локальный stop; доставка позже не возобновляет работу. Невозможность предупредить человека не должна препятствовать остановке.

**DIAG-10. Fault injection.** Реальные localhost socket refusal/reset, forced subprocess exit, controlled latency/lost ack, isolated DB restart, synthetic 401/429, disk quota/cgroup test и restart в середине backoff. Clock abstraction допускает ускоренный unit тест, но есть хотя бы один wall-clock integration test. Проверяется счётчик вызовов провайдера после stop, а не только статус UI.

## 26. Bootstrap: разработка продукта отдельным stock Symphony

**BOOT-01. Два контура.** Существующий DF Assistant/Symphony — вне изменений. Новый bootstrap экземпляр — отдельная OS/container identity, home, CODEX_HOME, queue, Git authorization, log/workspace roots, port и limits. Третий объект — разрабатываемый Symphony Next в собственных Coolify resources. Bootstrap не становится частью production runtime нового продукта и не обновляет себя по его webhook.

**BOOT-02. Baseline.** Установочный кандидат: официальный Symphony v0.0.3, source 1c0fb6c8e8ef9031a2c861e62af5f9e66cee39cb, asset SHA256 ea35a04a54a6d37c0cafe3f195da871e47614a8c05765b90dbb4cac32e1435ee. Codex — полный официальный npm bundle 0.155.1, включая platform package и sidecars, а не одиночный CLI. Installed owner preflight подтверждает исходный stock checksum, но не переносит его secrets. Версии pinned, не называются latest.

**BOOT-03. Авторизация.** Новая identity получает собственную законную авторизацию модели и repo-scoped Git write. GitHub tracker token/app installation ограничены новым repo и минимальными issues/PR полномочиями; широкие постоянные PAT запрещены. Repo-scoped SSH key не является GitHub REST токеном. Новый login может требовать участия владельца; это не новое подтверждение разработческой цели. Не копировать ~/.codex, auth.json, sessions, global MCP config или чужие SSH profiles.

**BOOT-04. Skills.** Owner report от 2026-09-22 содержит 99 обнаруженных SKILL.md, включая cached Superpowers 6.4.1; scan truncated=true, origins для найденных записей не установлены. Это не полный аудит и не доказательство популярного upstream repo. Сохраняется inventory/hash и scope, для используемых skills нужны source/provenance, license, review и pin. До этого используются repository PROJECT_RULES/AGENTS; глобальные skills не импортируются автоматически. Skills не выдаются privileged tools и не превращают subprocess в отдельного разрешённого агента.

**BOOT-05. Пилот.** Установка сначала stopped; далее проверка UID/paths/ports/binaries/auth/Git permissions/runner limits. Только одна dependency-ready sandbox issue с отдельной меткой; max_concurrent_agents=1. Planner first формирует проверенный пакет уточнения задач, не всю систему одним изменением. Затем один implementer и независимый review. Не выдавать весь backlog рабочей меткой одновременно.

**BOOT-06. Честная граница upstream.** Stock v0.0.3 имеет memory-only blocked и cap задержки retry, а не гарантированный total attempt cap; max_turns не ограничивает число повторных запусков. Немодифицированному stock не приписываются durable остановки нового продукта. Bootstrap использует bounded pilot time/cgroup и запрещённый blind restart. Допуск unattended режима требует отдельного fault acceptance; это не причина менять старый DF runtime.

**BOOT-07. Переход на native.** Только после native tracker+adapter acceptance, drain bootstrap jobs и snapshot queue/workpads. Проверка missing/duplicate IDs, source→target mapping и count/hash; старые admission labels сняты до включения нового scheduler. Выполнение одной задачи двумя экземплярами не допускается. Старый bootstrap сохраняется stopped для rollback; автоматическое удаление не входит в миграцию.

**BOOT-08. Проверка текущей итерации.** Документы/backlog/script tests, CLI/binary smoke, stopped install, OS-user/service adoption, authentication, actual model turn, PR/checks, webhook release и full product acceptance — отдельные результаты. Ни installation directory, ни скачанный binary не называются рабочей автономной разработкой.
